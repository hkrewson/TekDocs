# Engineering Risk Register

This register turns known limitations into release obligations. A risk remains open until the owning milestone records implementation and verification evidence; a passing scanner or test suite does not close a broader architectural risk.

| ID | Concern | Why it matters | Required solution | Owning milestone(s) |
| --- | --- | --- | --- | --- |
| `TD-RISK-001` | RBAC and client assignment policy requires full-stack certification before client access. | Resolved for the entity foundation in `0.2.0`: one permission/role catalog, complete authenticated-route inventory, method-level Read-only/MFA denials, scoped custom roles and collections, assigned-only reachability, MSP-private audience, cost projection, recovery composition, and cross-tenant/client IDOR suites run as one certification gate. | Keep assignments attached to authenticated tenant memberships rather than Person/job-title records. Every future domain and client-portal route must extend the inventory plus allow, deny, cross-tenant, cross-client, assignment-bypass, field/audience, and privilege-escalation cases before release. | Entity/RBAC foundation certified in `0.2.0`; recurring per domain |
| `TD-RISK-002` | Active RLS must remain complete as the domain expands. | Resolved for the supported one-MSP installation boundary in `0.2.0`: model discovery must match an explicit forced-RLS, authorization-control-plane, or singleton classification. Forced RLS protects domain data; control-plane ownership/edges/actors use scoped managers, central policy, immutable database guards, negative API isolation, and migration-cycle certification. Control-plane reads remain outside RLS to permit tenant establishment and invitation redemption. | Keep the inventory blocking and require every new tenant-owned model to declare its boundary. A hosted multi-MSP topology requires a separately reviewed identity/control-plane isolation design and must not rely on this single-installation certification. | Single-installation foundation certified in `0.2.0`; recurring per model; hosted boundary future |
| `TD-RISK-003` | Browser journeys mostly mock APIs. | Component behavior can pass while cookies, CSRF, proxying, serialization, migrations, or PostgreSQL behavior fail in the real stack. | Maintain at least one isolated, non-mocked browser-to-proxy-to-Django-to-PostgreSQL journey for each delivered critical workflow, starting with organization drill-in. | `0.1.3`, every minor stabilization |

Document an operator-owned 1Password CLI injection recipe without granting the application vault access. | plan in `0.1.3`; implementation in `0.3.2`; production enforcement in `0.8.7` |

| `TD-RISK-006` | Supported backup/key recovery does not exist. | Loss of PostgreSQL, attachment volumes, or wrapping keys can permanently lose data or encrypted MFA/secret material. | Build encrypted backup/restore tooling, separate key custody, destructive-operation safeguards, integrity verification, and recurring restore/database/key-loss rehearsals. | `0.8.1`, `0.9.3` |

| `TD-RISK-009` | Reproducible inputs must become signed release provenance. | `0.1.14` adds reviewed hash locks for Python build/production/development dependencies, digest-pins external runtime/tool images, SHA-pins Actions, and locally verifies pin/workflow syntax while retaining Dependabot. | `TD-RISK-011` | The original hand-written router cannot safely scale to nested workspaces. | Dynamic organization routes, history, bookmarks, route errors, and later nested domains would accumulate fragile pathname conditionals. | Adopt a maintained router, central route definitions, explicit not-found behavior, dynamic workspace parameters, accessible links, and route-level tests. | `0.1.3` |
| `TD-RISK-012` | Workspace organization discovery required bounded, permission-filtered search. | Loading every organization would not scale and could disclose more selectable metadata than the user needs. | Resolved for the workspace switcher in `0.1.4` with validated server-side search/pagination/order, scoped results, cancellation/debounce, and negative tests. | `TD-RISK-013` | The editor bundle already exceeds the preferred chunk budget. | The feasibility editor is roughly 1.17 MB minified; more plugins, histories, and previews can slow startup and low-powered client devices. | Preserve lazy loading, split optional syntax/plugins, establish route/chunk budgets, measure representative devices, and remediate regressions. | `0.2.9`, `0.8.5` |

| `TD-RISK-015` | Logs are JSON-shaped rather than safely structured. | Arbitrary messages can break escaping and later leak or corrupt log ingestion if request/domain values enter message strings. | Adopt a maintained structured formatter, field allowlist/redaction tests, correlation fields, bounded retention, and failure-path review. | `0.6.6`, `0.8.7` |
| `TD-RISK-016` | Local frontend gates depend on an unchecked host Node version. | `make check` can fail before linting when an obsolete host Node is first on `PATH`, even though the project requires Node 24. | Add an explicit runtime doctor or containerized frontend gate so the documented one-command check either uses Node 24 or fails immediately with a precise remedy. | `0.1.3` |
| `TD-RISK-017` | Early performance evidence could drift from authorization and production growth. | A fast small fixture can conceal N+1 queries, over-broad cached results, or later degradation as unrelated client data grows. `0.1.15` establishes a 100-organization/10,000-record PostgreSQL tripwire, but it is not yet a capacity test for document revisions, assets, concurrent users, or hosted deployments. | Retain query-count ceilings around authorized services, keep the latency fixture in the release gate, add each new domain family to the dataset, prohibit cross-scope authorization caches, and complete controlled concurrency/search/load evidence on the full 1.0 reference dataset. | Initial baseline `0.1.15`; documentation history `0.2.9`; full load certification `0.8.5` and `0.9.4` |
| `TD-RISK-018` | Schema upgrades can preserve rows while weakening policy or relationship semantics. | A fresh database cannot prove that existing identifiers, archived state, custom-field versions, entity links, role assignments, audit evidence, or forced RLS survive a real migration. | Keep a representative PostgreSQL migration-cycle test beside fresh-install and oldest-supported upgrade rehearsals; require value-transforming migrations to add preservation assertions and require non-reversible migrations to document a forward-only recovery procedure. | Initial blocking cycle `0.1.15`; every schema milestone and final `0.9.3` upgrade certification |
| `TD-RISK-019` | The executable Markdown contract, in-app help, and GitHub Wiki can drift apart. | Authors may follow documentation that no longer round-trips or renders safely, while duplicated help can make security and portability promises contradictory. | Treat ADR 0019 plus the fixed fixture as the implementation source of truth; review every dialect change across editor, renderer, sanitizers, tests, and in-app help. Before public beta, publish end-user/operator material to the actual public GitHub Wiki, add link/drift validation, and expose stable contextual-help links without injecting remote executable content. | Initial contract `0.2.1`; stabilization `0.2.9`; Wiki/contextual help `0.8.8` |
| `TD-RISK-020` | External credential references can be confused with access grants or unsafe share links. | A user may assume a TekDocs reference grants vault access, or paste a public share/arbitrary URL that weakens custody and phishing boundaries. References can also become stale after a provider item moves. | Store no customer secret value; use a provider-specific allowlist beginning with 1Password Private Links; reject share links and arbitrary URLs; label references as pointers rather than access; retain scoped RBAC/value-free audit; and provide stale-item/operator guidance without adding a retrieval API. | Decision in ADR 0020; implementation `0.3.1`; stabilization `0.3.10` |
| `TD-RISK-021` | Managed attachments are validated but are not malware-scanned or quarantined. | Forced downloads, content signatures, strict allowlists, private storage, and the absence of inline rendering substantially limit exposure, but an authorized user can still upload and another authorized user can download a malicious file whose bytes match an allowed format. Local-volume storage also lacks the provider isolation and lifecycle controls expected of larger deployments. | Keep downloads forced and private; do not add inline active-content rendering or archive extraction. Add a provider-neutral storage boundary, asynchronous malware scanning with quarantine and fail-closed status, scan-result audit metadata without file content, safe retry/failure behavior, and an adversarial file-processing corpus before broadening attachment types. | Initial bounded contract `0.2.6`; implementation and corpus `0.3.8`; stabilization `0.3.10` |

## Release rule

Release evidence must name every risk assigned to that milestone and record it as `resolved`, `mitigated with remaining owner`, or `blocked`. Moving a risk requires updating both this register and the destination milestone; it may not disappear from a release note merely because feature work passed.
