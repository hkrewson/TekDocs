# TekDocs 0.9.1: repository foundation composed acceptance

Date: 2026-10-03. Application version is `0.9.1` after the composed repository
foundation rehearsal satisfied issue #98.

## Completed slice

Issues #92–#95 establish a stable repository control-plane identity, private
local custody, one bounded commit service, and deterministic portable workspace
identity without making the Git working tree, newest commit, or a remote service
an authorization authority.

- A workspace can bind to at most one repository UUID and storage-relative path.
- Repository, tenant, and workspace ownership must agree at both the application
  and PostgreSQL boundaries.
- Accepted and indexed heads can reference only immutable commit identities that
  were verified for that exact repository.
- Lifecycle, health, and reconciliation state are explicit and remain separate
  from authorization policy.
- Repository identities and verified commits are classified as guarded
  authorization-control-plane records rather than tenant-domain RLS tables.
- No repository path, host path, credential, or new repository-management route
  is added to the public API.
- Every existing and newly supported MSP or organization workspace receives one
  isolated bare Git repository in the managed persistent volume.
- Repository directories derive only from the stable repository UUID and reject
  traversal, symlinked storage, unexpected ownership and invalid entry types.
- Initialization is atomic and retry-safe, and repairs private directory/file
  modes without replacing an existing valid repository.
- Production containers retain read-only roots; only the migration, web and
  worker services mount the explicit repository volume, while the scheduler has
  no repository access.
- Application callers can read accepted file bytes and apply a bounded set of
  file replacements or deletions; they cannot supply Git commands or options.
- Repository writes use a cross-process lock, database row lock, expected-base
  compare-and-swap, fixed service identity, fixed Git command forms, constrained
  environment, time and output bounds, and byte/path limits.
- A Git ref advances only with an accepted database commit. Failed acceptance
  rolls the ref back, while a later call reconciles a crash-window ref to the
  last database-accepted head and removes private abandoned staging state.
- Repository-local configuration, alternate object stores, hostile refs,
  option-like paths, traversal and unsafe entry types fail closed. Errors and
  logs identify only the repository and fixed operation, not authored values.
- Every repository carries versioned `.tekdocs/repository.yml` and
  `.tekdocs/workspace.yml` files generated from PostgreSQL-owned identities.
- Only the MSP repository carries `.tekdocs/organizations.yml`, containing the
  stable organization, workspace and repository UUIDs plus display name and
  classifications for each organization. Organization repositories carry only
  their own identity.
- Manifest bytes are deterministic. Safe unknown fields survive regeneration,
  while aliases, duplicate or merge keys, custom tags, excessive structure and
  secret-shaped fields fail closed.
- Organization renames and classification changes refresh the projections
  without replacing any stable identity. Operational records, users, assets,
  contracts, permissions, audit data and credentials remain outside the files.

Issue #96 completed immutable authenticated commit attribution, accepted-head
reconciliation, last-known-good reads, aggregate health and explicit
repair-to-accepted behavior. Issue #97 extends the authenticated recovery set
with complete per-workspace Git bundles, retained verified commits, a portable
authority manifest, pre-destruction validation and network-isolated restore.
Issue #98 completes composed repository-foundation acceptance. No existing
document or operational record has been migrated into canonical repository
content yet; that remains explicitly outside `0.9.1`.

## Validation evidence

- Fresh migrations and migration drift check pass.
- Upgrade from the exact `0.9.0` schema, rollback, and reapply preserve the
  existing tenant and workspace identities.
- Application and PostgreSQL tests reject duplicate workspace bindings,
  cross-tenant bindings, unsafe paths, and foreign accepted heads.
- Tenant-model inventory, forced-RLS/control-plane guard inventory, lint, type
  checking, and OpenAPI drift checks pass.
- The repository path/failure corpus, supported MSP and organization creation,
  full frontend suite, lint, type checking and migration-drift gates pass.
- A restricted production runtime creates the repository as the unprivileged
  application user; image inspection confirms one shared explicit volume and
  read-only container roots.
- Forced backend recreation retains the same repository bytes and a subsequent
  initializer run retains, rather than replaces, the repository.
- Twenty-six focused service tests cover successful/no-op/delete commits,
  deterministic attribution, concurrent writers, stale bases, interruption and
  recovery, abandoned staging cleanup, hostile paths/refs/repositories, lock and
  content/output limits, and log redaction.
- The restricted production runtime commits and reads through the service,
  rejects a stale writer, verifies the fixed service identity, and reads the
  accepted bytes again after forced container recreation.
- Schema fixtures, byte-stability/no-op tests, hostile YAML limits, redaction,
  cross-tenant isolation, rename and supported create/update-path tests cover
  the portable manifests.
- The restricted production runtime creates and validates all three manifests,
  confirms that only the MSP has the organization directory, and preserves the
  repository state through backend recreation.
- Focused recovery tests retain unreachable verified commits, restore exact
  accepted heads, reject advanced repositories, malformed/truncated bundles and
  occupied destinations, and compare the restored repository inventory with
  PostgreSQL authority.
- Supported recovery pauses writers for a consistent database/repository
  snapshot, authenticates the repository component before destructive work,
  restores without a remote, and reconciles every repository after restore.
- The composed acceptance creates MSP, client and vendor repositories, proves
  deterministic portable manifests and rejected cross-repository reads,
  recovers an interrupted write, recreates backend and worker containers, and
  compares the exact repository/head/content inventory after encrypted restore
  on a Docker-internal network.

No deployment, GitHub integration, remote repository or document migration is
introduced by this slice.
