## WebKit draft-protection dialog

Historical hosted failures at 320, 1024 and 1280 pixels timed out while waiting
for the unsaved-changes dialog after a technician edited Document settings and
activated Files. Later unchanged hosted and local replays passed, so those runs
did not establish a cause.

The warning component was loaded through a lazy module boundary with a blank
Suspense fallback. That means the departure action could be correctly blocked
while no warning was present until a separate module finished loading. A focused
regression now requires the dialog to be present in the same departure interaction.
It failed against the lazy boundary and passed when the safety-critical dialog
became part of the initial navigation-guard code.

Evidence on November 13, 2026:

- Before the fix, the unchanged production-shaped WebKit journey passed 60 of 60
  repetitions across 320, 390, 768, 1024, 1280 and 1440 pixels with four workers.
  This confirms the hosted symptom remains intermittent under ordinary replay.
- The synchronous navigation-guard regression failed before the implementation
  change because no accessible dialog was present, then passed after the change.
- No timeout, selector, assertion, retry or expected-result allowance changed.

Disposition: the blank lazy-loading window is a real draft-protection defect and
is fixed in source. Final production-build WebKit replay and the exact-candidate
hosted lane still have to verify the resulting commit.

## Recurring-template document read

Historical hosted failures left a Git-backed document read pending for roughly
2.8 to 3.0 seconds inside a five-second content assertion. Unchanged replays then
passed. Earlier cumulative-suite exhaustion was separately corrected without
changing the per-case 120-second limit; it does not explain the later pending
read observations.

The November 13 full live browser/server rehearsal retained the original
single-worker order and 120-second per-case budget. Its recurring-template case,
`template sources retain copy, live and pinned enrollments through publication
and rollback`, passed in 39.0 seconds. The reviewed update acknowledgement in that
case took 5.134 seconds, which demonstrates meaningful real server latency even
though the case synchronized on the response and passed.

The same full rehearsal later encountered a different native-template symptom:
an update returned HTTP 409 after 5.124 seconds. Fourteen earlier live cases had
passed. An isolated replay of that native-template browser case passed unchanged
in 42.4 seconds; its server verifier correctly rejected the filtered rehearsal
because complete verification requires the full 15-case set. The isolated replay
is diagnostic evidence, not a passing release gate.

Disposition: the original recurring-template content assertion reproduced as a
pass, not a failure, and no evidence justifies weakening it. The later five-second
repository conflict indicates accumulated-suite contention at the repository
lock boundary but does not establish the exact holder or safe product correction.
The final complete local replay passed all 15 browser cases in 5.7 minutes with
zero retries, including server-side fixture verification, retained bytes and the
authority round-trip. The recurring-template case passed in 38.7 seconds, its
reviewed update acknowledgement took 5.086 seconds, and the later native-template
case passed in 42.5 seconds. This supports disposition as a monitored residual
latency/lock-contention risk for local acceptance; it does not prove the exact
holder in the earlier transient conflict. A repeat failure must retain safe phase
timings and be diagnosed at the repository lock boundary. It must not be retired
by increasing the assertion, test timeout, or retry count.
