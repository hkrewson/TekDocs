# Immediate Git-backed document and 1.0 closeout

Status: maintainer-approved scope revision, November 2, 2026; acceptance pending.

The 1.0 route is a clean Git-backed start with manual document migration. The
maintainer has only a few existing documents and accepts manual recreation
without automatic transfer of their identities, relationships or history. This
supersedes the earlier decision to require all six remaining legacy migration
shapes. Those gaps are recorded as optional backlog, not release blockers and
not implemented closures. No existing data is to be deleted.

## 1. Prepare and review the manual document copies

- Use the [Markdown copy tool](https://github.com/hkrewson/TekDocs/wiki/Markdown-document-copy)
  to save current accessible text to a private local folder. Review its index,
  expected document count, empty files, failures and native Git reference
  warnings; open each wanted document and compare it with the original.
- Separately download any wanted PDFs, attachments and primary files. Markdown
  copies do not preserve signed publication records, old revisions, file-version
  chains, permissions or independent reusable fragments. Copy required key
  values, diagrams and reusable content manually where needed.
- Recreate the wanted documents in the supported Git-backed interface. Rebuild
  desired links, reuse, bindings and client access explicitly. New documents
  receive new identities; copied text is not a continuation of a signed
  publication or a reconstruction of its original history.
- Keep the existing installation, database, repositories, publications, PDFs,
  files and volumes intact. Keep the normal backup available. This plan neither
  runs an export nor authorizes production inspection, provisioning, cutover,
  reset, archive removal, volume removal or deletion. Any later production
  change needs its own explicit authorization and concrete reviewed steps.

Exit: the maintainer has reviewed the wanted copies and the manual recreation
checklist. No automatic legacy handoff or historical-fidelity requirement is
implied. This acceptance is still pending; the exporter has only synthetic-test
evidence, not a completed production copy.

Use one bounded acceptance matrix for the workflows that will ship in 1.0.
Audit existing implementation and evidence first; fix demonstrated defects in
small slices rather than adding capabilities through the migration backlog.

and [primary-file controls](git-native-primary-files.md) now have exact-source
hosted evidence. Source `61908a2c` passed Build, CodeQL, Extended, thirteen

File versions, signed publications and PDFs are preserved. The recurring template
read and WebKit dialog timing failures passed unchanged replays; their causes
remain unknown and need investigation before aggregate 1.0 acceptance. Native
configuration follows, then clean-start acceptance. Other source-inferred gaps
need reproduction before fixes. No production copy, existing-data change,
deployment or final operator acceptance is claimed; review actual counts/copies
and use the corrected server/exporter together.

## 3. Complete 1.0 candidate acceptance and freeze

- Freeze one candidate and run the maintained browser/accessibility matrix,
  performance, DAST, production-image, fresh-install and supported-upgrade gates.
  Removing automatic document migration blockers does not waive database-schema
  upgrade, isolation, integrity or backup/restore checks.
- Exercise installation, onboarding, daily Git-backed work, unavailable/conflict
  states and independent encrypted recovery with repositories, indexes, files
  and publications. Local work uses the existing development Compose project;
  gates needing an additional environment remain hosted unless separately
  authorized.
- Complete applicable human keyboard, touch/mobile, screen-reader and 200% zoom
  walkthroughs. Automated passes do not substitute for human acceptance.
- Complete commit-matched security review and explicit risk dispositions,
  including bounded exceptions and development-tool remediation. Do not extend
  expired or candidate-specific risk acceptance by changing this plan.
- Reconcile Wiki drafts, OpenAPI, the support contract, roadmap, release notes
  and evidence. State the manual transition boundary clearly; do not advertise
  comprehensive automatic migration of legacy documents. External pilots remain
  excluded by the October 20 scope decision.
- Record the maintainer's 1.0 release decision and compatibility freeze.
  Publishing, pushing and production changes follow their separate authorization
  and delivery rules; this planning change performs none of them.

Exit: exact-candidate checks, human acceptance and risk decisions agree. Any
remaining blocker is named with an owner and exit criterion. Historical passes,
manual document copies and a clean installation alone do not establish 1.0
acceptance.
