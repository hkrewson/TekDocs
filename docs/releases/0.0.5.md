# TekDocs 0.0.5 invitation issuance evidence

Date: 2026-08-07

Status: verified locally; hosted GitHub workflows remain pending publication.

## Delivered scope

- Owner-only API endpoints list, issue, revoke, and resend tenant-scoped invitations without opening public registration.
- The invitation model retains lifecycle and delivery metadata, permits only one pending record per tenant and normalized address, and preserves expired and revoked records for audit.
- Tokens use 256 bits of randomness, are stored only as SHA-256 digests, compared in constant time, rotated on resend, and cleared on observed expiry or revocation.
- Acceptance links place token material in the URL fragment so ordinary HTTP and proxy requests do not receive it. API responses and audit metadata contain no token.
- Multipart invitation templates use the central transactional-email service. SMTP failure retains a pending record for explicit resend and returns a generic, value-free error.
- Production validates the externally reachable invitation base URL, requires HTTPS by default, and bounds configurable invitation lifetime.
- The authenticated installation-owner check now crosses a shared policy boundary used by both the application context and invitation endpoints.

## Verification

- `make check`: passed Ruff, mypy, migration drift, OpenAPI drift, frontend lint/type checks, 23 frontend unit/component tests with 85.53% statement coverage, and the production build.
- `make test`: passed 56 backend tests with two PostgreSQL-only concurrency skips and 90.36% aggregate coverage, plus all 23 frontend tests.
- `make test-compose`: applied the invitation migration, returned ready status at version `0.0.5`, confirmed SMTP delivery through Mailpit, and passed all 58 backend tests against PostgreSQL with 93.80% aggregate coverage.
- PostgreSQL tests proved simultaneous duplicate issuance creates exactly one pending invitation; owner bootstrap concurrency also remained green.
- Authorization-negative tests deny anonymous and unrelated users and conceal cross-tenant invitation identifiers.
- Token tests prove digest-only persistence, expiry, resend rotation, revocation invalidation, duplicate rejection, existing-user rejection, value-free audit events, CSRF enforcement, and recoverable delivery failure.
- `make test-e2e`: passed six Chromium workflows, including accessibility checks and canonical Markdown editing.
- `make security`: passed `pip-audit`, Bandit with zero findings, npm production audit, Gitleaks with no leaks, and blocking High/Critical Trivy scans for the backend, frontend, and pinned Mailpit image with zero findings.
- OpenAPI generation and drift validation passed with the invitation contracts and version `0.0.5`.

## Boundaries carried forward

- Invitation token consumption, account creation, password selection, browser activation, and verified allauth email creation remain `0.0.6`.
- Public signup remains closed. An invitation email sent by `0.0.5` cannot yet activate an account.
- Invitation mail is synchronous. Automatic retry, an event outbox, background delivery, bounce handling, and notification preferences remain later roadmap work.
- Invitation management is API-only in this slice; the owner administration interface follows after the activation contract is complete.
