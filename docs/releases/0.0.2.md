# TekDocs 0.0.2 installation bootstrap evidence

Date: 2026-08-07

Status: verified locally; hosted GitHub workflows remain pending publication.

## Delivered scope

- A normal Django migration creates a constrained singleton installation-state row.
- The first-owner service holds a PostgreSQL `SELECT FOR UPDATE` row lock while it creates one tenant, one normal product owner, and one value-free audit event.
- `GET /api/v1/bootstrap/status` exposes only `bootstrap_required`.
- `POST /api/v1/bootstrap/owner` requires a high-entropy deployment value in `X-TekDocs-Bootstrap-Token`, uses constant-time comparison, validates the owner password, and closes permanently after success.
- Missing/wrong authorization, weak or invalid inputs, repeated claims, concurrent claims, non-pristine databases, and public signup fail closed.
- Production settings reject a missing or weak bootstrap token. `make bootstrap` creates it for a new environment or appends only that missing value to an existing environment without replacing other configuration.
- The generated OpenAPI contract documents the bootstrap header, request, response, and failure statuses.

## Verification

- `make check`: passed Ruff, mypy, migration drift, frontend lint/type checks/unit coverage, and production build.
- `make test`: passed 19 backend tests with 87% aggregate coverage plus 14 frontend tests. The PostgreSQL-only concurrency case is intentionally skipped by the SQLite fast suite.
- `make test-compose`: passed migrations, health, Django deployment checks, and all 20 backend tests against PostgreSQL with 90% aggregate coverage. The two-request bootstrap race produced one `201`, one `409`, one tenant, and one owner.
- `make test-e2e`: passed all three Chromium workflows.
- `make security`: passed `pip-audit`, Bandit with zero findings, npm production audit, Gitleaks with no leaks, and High/Critical Trivy scans for both images with zero findings.
- Production negative validation: starting Django with an empty `TEKDOCS_BOOTSTRAP_TOKEN` failed with `ImproperlyConfigured` naming the missing setting and no value.
- Runtime status: migration `core.0002_installationstate` is applied and the proxied status endpoint returned only `{"bootstrap_required":true}`.

## Boundaries carried forward

- `0.0.2` intentionally has no browser bootstrap or authenticated application boundary; those form `0.0.3`.
- Product role assignment and the central authorization service arrive in later scoped RBAC slices. The bootstrap identity is deliberately not a Django superuser, preventing an implicit bypass around that future policy boundary.
- Invitations, email verification/reset, MFA, session administration, and OIDC remain separate roadmap slices.
- The deployment token should be rotated after the first successful claim and its replacement retained in the deployment secret store for production validation. Database state, not continued possession of the token, determines whether bootstrap is closed.
