## How to use this guide

Work in short sessions. First do setup and the document journey; then the other
workspaces; then repeat the shared journey using each accessibility profile.
Finish with a realistic pilot. You do not need to run Docker or security scans.

Check a box only when its expected result holds. Record **Fail**, **Blocked**, or
**Not run** in the notes for anything you cannot complete. A missing fixture or
unavailable screen reader is a blocker, not a pass. We will turn your observations
into fixes and identify exactly which checks need repeating.

Do not enter passwords, MFA/recovery codes, real client information, or private
file contents here. Redact screenshots before sharing them. Use synthetic records.

## 3. Git-backed Documentation and Files

Use the document confirmed during setup; repeat the core read/edit/return path
in MSP and Acceptance A. Use two tabs only for the explicit conflict check.

- [ ] **Read and edit:** open the document and append a heading, a short checklist,
  and a fenced code sample. Include intentional blank lines and indentation.
  Save, reload, and reopen editing. Expected: exact Markdown is retained and the
  rendered page remains readable; a successful save has an identifiable revision.
- [ ] **History:** make a second small edit, save, and inspect history/diff.
  Expected: both changes are distinguishable and the displayed current version
  agrees with the reader. Do not rewrite Git history or reset the repository.
- [ ] **Links and backlinks:** use the supported link picker to link a second
  document and an asset. Follow each link and inspect related/backlink views.
  Expected: the intended records open in the same permitted workspace; returning
  preserves context. Record any link type the interface does not offer.
- [ ] **Reusable content:** insert the prepared fragment using the offered control,
  then update the fragment. Expected: the composition follows its declared
  current/pinned revision behavior. Record what revision policy is displayed;
  do not assume a pinned publication should change with live content.
- [ ] **Ordinary attachment:** upload the harmless test file, insert its offered
  Markdown link, save the document, then download it. Expected: the draft link
  is not mistaken for saved content; the downloaded bytes match the uploaded file.
- [ ] **Primary-file history:** inspect both prepared versions and download each.
  Expected: the chosen current version and its predecessor are clear; the older
  retained file is still available to an authorized user.
- [ ] **Files round trip:** search Files for the off-page item, open its owning
  document, and use browser Back. Expected: the same file search and result return.
- [ ] **Exports:** export the test document in the offered formats, including PDF
  and editable bundle where available. Open the results. Expected: headings,
  lists, links and prepared diagrams are readable, and file inclusion matches
  the selected export. An editing bundle must not claim to be a full backup.
- [ ] **Conflict:** open the same saved revision in tabs A and B. Save a harmless
  change in A, then attempt to save a different change from stale tab B.
  Expected: B does not silently overwrite A; B's draft survives and recovery
  choices are understandable. Resolve explicitly and verify the saved result.
- [ ] **Offline draft:** after loading the editor, set the browser's developer
  tools Network panel to Offline, edit, and attempt one save. Restore Online.
  Expected: no false success; the draft survives; an explicit retry saves once.
  This checks a browser connection failure, not a server-side repository outage.
- [ ] **Repository unavailable/index lag:** ask me to prepare this state in the
  isolated acceptance installation. Expected: a clear unavailable/not-ready
  state with draft preservation, never stale legacy content labeled current.
  Do not stop production services or delete repository files yourself.
- [ ] **Review and publication:** on synthetic content, request/review the
  publication using the distinct staff accounts, create the STATIC publication,
  release it and authorize delivery using the offered controls. Complete recent
  authentication when requested. Expected: pending, reviewed, released and
  deliverable states are distinguishable; authoring is not confused with approval.
- [ ] **Client view:** sign in as the A-only client in a separate profile. Open
  the released publication/PDF/file. Then change the live source as staff.
  Expected: the retained publication does not silently change; no MSP/B content
  appears. Withdraw the synthetic publication with a reason and confirm client
  access stops while authorized staff can still inspect retained evidence.
- [ ] **Templates:** inspect a prepared template and create a disposable document
  from it where supported. Expected: template controls, resulting content and
  reusable references are understandable. Record any unsupported path as blocked.

Questions: Did you ever wonder whether you were viewing live content, a draft,
or a retained publication? Were conflicts recoverable without losing work?
Which Git/history/link terms were unclear? Did Files lead where you expected?
