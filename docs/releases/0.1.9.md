# TekDocs 0.1.9 central policy and organization access evidence

Date: 2026-08-08

Status: verified locally; hosted GitHub workflows remain pending publication and a pull request.

## Delivered scope

- One central policy service owns the maintained permission catalog, built-in role definitions, MFA requirements, request authorization, and policy-filtered organization visibility.
- Owner, Administrator, Technician, Contributor, Read-only, Client Administrator, and Client User have explicit definitions. Tenant memberships accept only tenant-scoped roles; organization-scoped client roles remain reserved for `0.1.10`.
- Existing and new non-owner tenant memberships default or migrate to Read-only. Database constraints reject invalid tenant-role values.
- Organizations expose explicit `all_authorized` and `assigned_only` MSP-staff access modes. Assigned-only fails closed for non-owners until individual assignments arrive in `0.1.10`.
- Authentication context exposes stable permission keys, while domain APIs, workspace resolution, organization search, entity search, and relationship traversal apply the same central policy boundary.
- Owner-plus-MFA, CSRF-protected APIs expose the catalog, tenant members, role changes, organization access modes, and access-mode changes without allowing owner reassignment, arbitrary roles, self-escalation, or cross-tenant mutation.
- The Access Control page documents all built-in roles and provides confirmed tenant-role and organization-access changes with loading, error, denial, responsive, and accessible states.
- Role and access-mode changes produce value-free audit events. Mutation authority remains server-side even when the corresponding frontend control is hidden.

## Assigned risk disposition

- `TD-RISK-001` — **partially mitigated.** Central permissions, built-in tenant roles, and organization access modes now replace owner-only and inline authorization decisions. Custom roles and explicit tenant/client/collection assignments remain `0.1.10`.
- `TD-RISK-002` — **still open.** Policy-scoped application services and PostgreSQL integrity guards are active, but the non-owner runtime-role RLS boundary remains `0.1.12`.
- `TD-RISK-003` — **resolved for this workflow; recurring obligation remains.** The real browser journey and independent database assertion prove an access-mode mutation through the proxy, Django, migrations, and PostgreSQL.

## Known boundaries

- `assigned_only` deliberately permits only the installation owner in this slice. Explicit per-client MSP staff assignments arrive in `0.1.10`; silently treating an MSP-wide role as an assignment would weaken the boundary.
- Client Administrator and Client User are cataloged but cannot be assigned through tenant membership APIs. Their organization-scoped assignment model also arrives in `0.1.10`.
- Built-in roles are maintained product policy, not customizable records. Custom roles must compose catalog permissions without bypassing tenant, organization, classification, or MSP-private constraints.
- Local Compose intentionally permits HTTP and therefore reports Django's HTTPS-redirect deployment warning. The production-image rehearsal enforces the production settings contract.
- PostgreSQL RLS, database-enforced audit immutability, secret-file enforcement, reproducible supply-chain inputs, backups, hosted automation evidence, and the editor bundle warning remain tracked in the engineering risk register.
