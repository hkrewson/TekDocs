## Reviewed source boundaries

- DRF 3.18.3 replaces vulnerable 3.17.2 in both Python locks. DOMPurify 3.4.17
  resolves the frontend and renderer findings. Puppeteer 25.16.0 selects the
  compatible patched Zod chain. Mermaid and Chromium-major contracts remain.
  See [reproductions and Docker evidence](drf-security-maintenance.md).
- Publication is restricted to a versioned main push; PRs cannot publish.
  Required Build, CodeQL and extended validation precede publication. Images
  are transferred from the successful image build and scanned before publishing.
- The finalizer rejects conflicting commit images and version aliases, verifies
  each digest and signed attestation against the exact source commit, main ref
  and Build workflow, then atomically pushes application and companion tags.
  Registry and Git publication are not one transaction: a failure can leave
  partial registry images and must remain a failed release.
- Receipt retrieval parses data without executing it, requires four images,
  exactly one parent matching the application commit and exactly one changed
  receipt path. Existing backup, forward-upgrade and running-image checks remain.
  Receipt trust is the configured Git origin; the receipt tag is not signed.
- Clock-controlled historical tests retain a separate expiry rejection check.
  Fixture path naming and readiness-poll comments change no production behavior.

No new release-blocking defect was identified in this bounded delta review.
Historical reviews cover inherited application changes. Preserve ancestry when
bringing the branch to main; squashing would break the updater's forward-history
relationship to previously published candidate commits.

## Operator handoff after successful publication

Install the new updater once from the published application tag, preserving a
clean checkout and saved backup configuration:

```bash
git fetch origin tag v0.9.12
git switch --detach v0.9.12
scripts/update-production.sh --release v0.9.12
```

These commands are for after CI publishes both tags. The updater obtains the
receipt automatically; no manual receipt commit or Compose edit is required.
Do not run the update before the successful release summary is available.
