# Engineering Risk Register

This register turns known limitations into release obligations. A risk remains open until the owning milestone records implementation and verification evidence; a passing scanner or test suite does not close a broader architectural risk.

| ID | Concern | Why it matters | Required solution | Owning milestone(s) |
| --- | --- | --- | --- | --- |
| `TD-RISK-001` | RBAC and client assignment policy requires full-stack certification before client access. | `0.1.9`–`0.1.12` provide the central catalog/service, built-in roles, fail-closed organization access modes, explicit same-tenant MSP staff assignments, additive tenant/organization/collection custom roles, a hard MSP-private audience boundary, and the first sensitive-field projection seam. `0.1.13` adds a complete route inventory and blocking generalized anonymous, non-member, insufficient-role, MFA, CSRF, and identifier matrix; domain semantic suites cover cross-tenant, sibling-client, and assigned-only cases. Future domain families still require equivalent certification before client access. | Keep assignments attached to authenticated tenant memberships rather than Person/job-title records; extend the proven audience and field-policy seams to each new domain model and retain allow, deny, cross-tenant, cross-client, assignment-bypass, and privilege-escalation certification. No client portal or broad co-authoring may ship before certification. | Current route families certified in `0.1.13`; extension and stabilization remain `0.2.0` |
| `TD-RISK-002` | PostgreSQL RLS is not active. | Scoped managers and integrity triggers are strong application conventions, but unscoped managers, raw SQL, commands, or future code can bypass them. | Activate `USING` and `WITH CHECK` policies under a non-owner/non-`BYPASSRLS` runtime role; constrain bootstrap/token/worker paths and prove raw-SQL isolation plus pooled-connection cleanup. | `0.1.14`, `0.2.0` |
| `TD-RISK-003` | Browser journeys mostly mock APIs. | Component behavior can pass while cookies, CSRF, proxying, serialization, migrations, or PostgreSQL behavior fail in the real stack. | Maintain at least one isolated, non-mocked browser-to-proxy-to-Django-to-PostgreSQL journey for each delivered critical workflow, starting with organization drill-in. | `0.1.3`, every minor stabilization |

| `TD-RISK-007` | Runtime evidence does not exercise the production image contract. | The default stack builds the backend development target and runs migrations during web startup; dev dependencies and concurrent migration behavior can differ from a release deployment. | Add an isolated production-target smoke rehearsal now; later separate migration execution, pin runtime images, minimize packages/capabilities, run as non-root/read-only where practical, and verify the exact release image. | rehearsal in `0.1.3`; hardening in `0.8.7`; release proof in `0.9.4` |

| `TD-RISK-009` | Python and runtime supply chains are not reproducibly pinned. | Compatible ranges, mutable base-image tags, mutable local scanner tags, and tag-based GitHub Actions can resolve different code for the same commit. | Add a hashed Python lock, digest-pin release bases/tools, SHA-pin Actions, preserve automated updates, verify licenses, and attest the resulting images/SBOMs. | `0.1.14`, `0.8.7`, `0.9.4` |
| `TD-RISK-010` | Hosted GitHub automation is unverified. | Workflows exist, but without a configured remote and observed runs, CodeQL, dependency review, browser matrices, and artifacts are specifications rather than evidence. | Publish/configure the repository when authorized, protect the main branch, require the documented checks, and retain the first successful hosted evidence. | `0.1.14` (externally blocked until publication is authorized) |
| `TD-RISK-011` | The original hand-written router cannot safely scale to nested workspaces. | Dynamic organization routes, history, bookmarks, route errors, and later nested domains would accumulate fragile pathname conditionals. | Adopt a maintained router, central route definitions, explicit not-found behavior, dynamic workspace parameters, accessible links, and route-level tests. | `0.1.3` |
| `TD-RISK-012` | Workspace organization discovery required bounded, permission-filtered search. | Loading every organization would not scale and could disclose more selectable metadata than the user needs. | Resolved for the workspace switcher in `0.1.4` with validated server-side search/pagination/order, scoped results, cancellation/debounce, and negative tests. Apply the same convention API-wide in `0.6.1`. | Resolved in `0.1.4`; API-wide convention in `0.6.1` |
| `TD-RISK-013` | The editor bundle already exceeds the preferred chunk budget. | The feasibility editor is roughly 1.17 MB minified; more plugins, histories, and previews can slow startup and low-powered client devices. | Preserve lazy loading, split optional syntax/plugins, establish route/chunk budgets, measure representative devices, and remediate regressions. | `0.2.9`, `0.8.5` |
| `TD-RISK-014` | Editor/example changes remain outside Git history. | The current working interface and tests can differ from a clean checkout, making evidence harder to reproduce and the work easier to lose. | Keep these user-owned changes isolated from unrelated slices, then explicitly review and commit them with the Markdown fixture contract or deliberately discard them with user approval. | `0.2.1` entry criteria |
| `TD-RISK-015` | Logs are JSON-shaped rather than safely structured. | Arbitrary messages can break escaping and later leak or corrupt log ingestion if request/domain values enter message strings. | Adopt a maintained structured formatter, field allowlist/redaction tests, correlation fields, bounded retention, and failure-path review. | `0.6.6`, `0.8.7` |
| `TD-RISK-016` | Local frontend gates depend on an unchecked host Node version. | `make check` can fail before linting when an obsolete host Node is first on `PATH`, even though the project requires Node 24. | Add an explicit runtime doctor or containerized frontend gate so the documented one-command check either uses Node 24 or fails immediately with a precise remedy. | `0.1.3` |

## Release rule

Release evidence must name every risk assigned to that milestone and record it as `resolved`, `mitigated with remaining owner`, or `blocked`. Moving a risk requires updating both this register and the destination milestone; it may not disappear from a release note merely because feature work passed.
