# Architecture

## Runtime

TekDocs ships as a same-origin web application. Nginx serves the React build and proxies `/api/`, `/accounts/`, `/admin/`, and `/static/` to Gunicorn. Celery workers and the scheduler share the Django codebase. PostgreSQL is the system of record; Valkey supplies task transport and cache primitives.

The default Compose services are `db`, `valkey`, a one-shot `migrate` job, `backend`, `worker`, `scheduler`, and `frontend`. The migration job owns schema changes and provisions the fixed `tekdocs_runtime` login; application processes receive only that non-owner credential. Persistent application artifacts use a storage provider: local volumes initially and S3-compatible storage later.

## Domain direction

`Tenant` is the one-MSP installation boundary and a future hosted seam, not a currently supported multi-MSP hierarchy. Each tenant has one immutable MSP `Workspace`, and each `Organization` has one immutable organization Workspace. `Entity` is the universal stable UUID and required canonical ownership anchor; typed models attach to it. `EntityLink` supplies referential relationships without generic foreign keys. Tenant/organization columns remain denormalized scope inputs for indexes, RLS, and relationship guards, while the non-null Workspace UUID makes accidental owner omission fail closed. ADR 0035 defines this boundary.

Canonical documentation content is Markdown. ADR 0019 freezes the supported dialect and visual-editor contract: editor HTML/JSON is transient, while semantic highlight and typed callouts serialize to readable text extensions. Preview crosses an authenticated, permission-cataloged Django rendering boundary with raw HTML disabled, an explicit `nh3` allowlist, bounded input, and a second DOMPurify allowlist in the browser. The fixed round-trip corpus combines realistic technical documentation with every supported extension. `Document`, `Block`, and ordered `DocumentPlacement` records persist with stable identity and explicit tenant/workspace ownership. Canonical Markdown lives only in append-only `BlockRevision` rows. Each revision has a sequential number, parent, SHA-256 checksum, author, and timestamp; `Block.current_revision` is the locked resolution pointer. Updates submit the exact base revision, and stale writes return a non-destructive conflict plus a server diff.

Customer credential values remain outside TekDocs. ADR 0020 defines provider-specific, permission-aware references beginning with 1Password Private Links; reveal and vault authorization stay in the external provider. Deployment secrets are a separate runtime input supplied through files or an operator-controlled secret manager.

`EntityLink` types are selected from a maintained catalog with forward/inverse labels, target-type rules, and canonical handling for symmetric links. Relationship reads resolve both outgoing links and incoming backlinks through the same URL-derived workspace visibility service used by bounded Entity search. An organization workspace may discover active MSP-owned organization anchors for explicit relationships, but never sibling-owned child records. PostgreSQL guards same-tenant endpoints, empty metadata, immutable identity, canonical symmetry, and immutable archival. ADR 0011 defines the full relationship and search contract.

Supplier catalogs and operational inventory use an explicit provenance boundary. `CatalogProductDocument` connects one product and optional model to one exact supplier-owned, client-visible STATIC publication. `ClientAsset` (a compatibility-era internal name) is a separately owned operational entity that freezes exact supplier, product, model revision, specification version, validated values, and checksum at creation. `ClientAssetDocumentProvenance` freezes each applicable association, publication, and digest. Client and MSP modes receive a narrow read-only RLS projection of supplier catalog rows and associated client-visible publication artifacts so asset creation works without changing active workspace scope; ordinary supplier documentation remains invisible. Vendor views derive from retained supplier identifiers rather than copied records or mutable labels. ADR 0030 defines provenance and ADR 0034 defines owner parity.

Asset CSV transfer is an API workflow over the inventory domain, never a table dump. The versioned exact-header contract allowlists mutable asset identity/lifecycle fields and excludes every credential, cost, contract, license, attachment, assignment, disposal, and internal provenance payload. Dry run returns permission-scoped row actions and a short-lived signed binding over file, Workspace, and action digests; apply reparses in one transaction. Deterministic UUIDv5 identity derived from a Workspace and operator-stable import key makes create retries idempotent without retaining uploaded CSV bytes. Export escapes spreadsheet-formula-shaped cells. ADR 0037 defines the boundary.

Inventory collection reads share one bounded page contract after exact Workspace resolution and central-policy authorization. Assets, software licenses, contracts, and credential references return stable pages of at most 100 rows with exact count and continuation metadata; MSP routes select only the explicit MSP Workspace and never aggregate client rows. Related inventory data is selected or prefetched in a fixed number of queries. The combined PostgreSQL reference fixture and certification gate exercise pagination, concurrency, recovery, protected-field omission, credential-pointer lifecycle, upgrade, and restore behavior. ADR 0038 defines this stabilization boundary.

Network inventory currently retains the addressable models introduced by ADRs 0040–0044: racks/devices and placement, VLAN/VRF/subnet routing data, interface/IP/MAC assignments, wireless/DNS inventory, and provider circuits/handoffs. All remain exact-Workspace records under central policy, forced RLS, relationship guards, and conflict serialization. Product direction changed after those pre-1.0 slices: TekDocs will keep common MSP facts and use NetBox for deeper DCIM/IPAM rather than becoming a second NetBox. The `0.4.8` migration owns the deliberate preservation and simplification of ordinary workflows; existing tables are not silently dropped or reinterpreted in `0.4.7`.

`NetBoxReference` establishes the narrow cross-system identity seam. It binds one active exact-Workspace TekDocs Entity to one NetBox `app_label.model` content type and positive numeric primary key, following NetBox's public object identity convention. The initial allowlist maps racks, hardware Assets as devices, MAC addresses, VLANs, prefixes, and IP addresses; it deliberately excludes Interface and VRF mappings. A bounded normalized fingerprint preview reports current, changed, unmatched, and missing-remote states without persisting arbitrary remote JSON or mutating either system. No URL, token, outbound request, job, or write-back exists in this slice. ADR 0045 defines the boundary.

`Person` is one tenant-wide human identity attached to an MSP-scoped `Entity`. `PersonAssociation` records employment or contact context in exactly one URL-selected workspace: a null organization is the MSP, while a non-null organization is that client or supplier. Descriptive role and responsibility fields never grant permissions. Database triggers reject person/entity/organization tenant mismatches, and ordinary reads use the same fail-closed scoped manager contract as other organization-owned records. ADR 0008 defines future user linkage and client-assignment policy.

`CustomFieldDefinition` supplies a stable MSP-wide or organization-specific key for one Entity type. Immutable `CustomFieldDefinitionVersion` rows contain server-generated JSON Schema and presentation metadata. Entity values remain in the existing `Entity.custom_fields` JSON object as a strict envelope containing the exact validating version ID, sequential version number, and value. PostgreSQL guards enforce tenant, organization, target-type, version, and envelope consistency; application validation provides operator-friendly errors. MSP definitions are inherited by matching organization-owned entities, while organization definitions never cross their owning workspace. ADR 0010 defines the complete versioning and inheritance contract.

`Site` is an addressable MSP- or organization-owned facility with address, timezone, phone, and operator code metadata. `Location` is an addressable building, floor, suite, room, office, desk, or area in one site's parent-child tree. Database triggers enforce identical workspace scope across entity, site, location, and parent records and reject hierarchy cycles. Person associations can reference an active site/location while retaining free-text location and office snapshots for unmapped imports and historical display. ADR 0009 defines this placement contract.

Tenant-owned domain reads use explicit scoped managers. Omitting the tenant from a scoped manager fails before SQL is issued; organization-scoped queries match the tenant, the exact selected Workspace, and its organization projection. An `Organization` record is attached to an MSP-owned anchor Entity and has a separate immutable ownership Workspace for its child data. Its normalized classifications allow the same business to act as a client, vendor, manufacturer, partner, or any valid combination without duplicating identity. Archive-on-delete retains the organization, entity, workspace, child ownership, and inbound references; protected relationships prohibit physical deletion from orphaning owned data.

Authorization flows through `apps.accounts.policy`: callers request a stable permission key and may supply a route-resolved organization, while the policy service resolves membership, built-in role, organization access mode, explicit MSP staff assignment, and any MFA requirement. Production callers do not inspect role names. The immutable installation owner has every permission; tenant memberships may be Administrator, Technician, Contributor, or Read-only. Client Administrator and Client User are cataloged organization roles but remain unassignable until the later scoped-role model. Existing and newly accepted memberships default to Read-only.

Every organization records an MSP-staff access mode. `all_authorized` allows a tenant member only when the member's role also grants the requested permission. `assigned_only` preserves owner break-glass access and otherwise requires an explicit assignment to the authenticated tenant membership. Lists, switcher search, direct routes, domain queries, entity search, and relationship traversal use the same policy-filtered organization boundary. Assignment satisfies only this boundary; it never grants a missing permission or substitutes for MFA. ADRs 0012 and 0013 define the staged contract.

Custom roles add bounded permissions at tenant, exact-organization, or access-collection scope. An access collection is an authorization-only grouping of active organizations; changing its membership changes every associated grant immediately. Collection grants remain additive and cannot bypass an organization's `assigned_only` staff edge. Universal entities default to `msp_private`; the audience policy permits client projection only for `client_visible` entities owned by that exact organization. Sensitive fields use a separate catalog-driven projection seam: `cost` maps to `costs.view` and is omitted entirely when denied. ADRs 0014 and 0015 define these composition rules.

Commercial contracts are MSP- or client-owned Entities related to one same-tenant vendor, manufacturer, or partner organization. Operational contract identity, lifecycle, term, renewal, and notice fields remain distinct from `ContractCost` rows. The latter use fixed-precision values and are projected as one sensitive `cost` field: without exact-scope `costs.view`, the response member is absent. Contract list/search never joins, filters, orders, aggregates, or counts cost data. Mutating a cost composes MFA-protected `assets.edit` with `costs.view`; PostgreSQL relationship guards and forced RLS backstop exact workspace ownership. ADR 0033 defines the financial boundary and ADR 0034 defines MSP ownership.

Ordinary archived organization, person-association, site, location, and custom-field-definition records enter a route-scoped recycle bin. Recovery composes the central recovery grant with the domain's original archive/manage grant, organization reachability, MFA, and CSRF. Site and location cascades share an archive timestamp so recovery cannot revive descendants archived in an earlier operation. Audit events remain outside the recycle bin and PostgreSQL rejects their update or delete. ADR 0016 defines the recovery and immutability contract.

Every authenticated API route is listed in a maintained permission inventory with its supported methods, read/mutation permissions, and organization-scope shape. A blocking generalized matrix verifies route coverage, anonymous/non-member denial, insufficient-role denial, MFA, CSRF, and identifier parsing, while domain semantic suites retain cross-tenant, sibling-client, and assigned-only fixtures. Adding a route without inventory coverage fails the suite.

Workspace context is an explicit URL and query boundary, not ambient authorization stored in a browser or server session. The MSP workspace selects tenant-owned records whose organization scope is null. An organization workspace selects that organization's owned records through both tenant and organization identifiers after policy authorization. Organization anchor records remain MSP-owned so they can be discovered and selected without making their child data visible. Opening separate browser tabs in different workspaces cannot alter either tab's scope.

The shell derives its workspace label and available sections from organization classifications. A multi-classified organization receives the union of applicable navigation capabilities and displays every applicable classification; vendor, manufacturer, and partner are retained as classifications rather than separate table hierarchies. Hidden navigation is only presentation—every endpoint, worker, search result, backlink, export, and creation path independently enforces the selected scope.

PostgreSQL scope helpers consume transaction-local tenant, Workspace, organization, and organization-mode settings. The non-owner, non-`BYPASSRLS` runtime role is subject to forced `USING` and `WITH CHECK` policies on every implemented core tenant-owned table. Authenticated session requests run inside one transaction: the server derives and binds the installation tenant and MSP Workspace, then, after Django's CSRF view check, resolves an organization route within that tenant before rebinding its exact Workspace scope. The view's central-policy decision remains authorization; selecting database scope alone grants nothing. Missing scope and runtime attempts to select an unrestricted `all` mode fail closed; committed scope values cannot survive connection reuse. Immutable Workspace identity, same-tenant organization anchors, entity ownership, and entity-link endpoints retain database integrity triggers as an additional layer.

The `0.2.0` certification inventory classifies every tenant-bearing model. Entity-domain tables use forced RLS. Invitation, membership, role, assignment, and collection tables form the authorization control plane and remain outside RLS because they establish the tenant and policy context needed before domain scope can be bound; the installation singleton is a separate bootstrap boundary. Fail-closed managers, central policy, API/IDOR isolation, immutable tenant ownership, same-tenant database edges, and same-tenant actor attribution protect this control plane. This is certified for one MSP per installation, not a hosted multi-MSP control plane. ADRs 0006, 0017, and 0018 define the full boundary.

Python production, development, and build inputs are checked in as hash-locked requirements. External container bases, Compose services, browser images, and local scanners are digest-pinned; GitHub Actions are commit-SHA pinned with release annotations. Dependabot remains the controlled update path, while local pin and workflow-lint gates reject a return to mutable inputs. Hosted workflow results are evidence only after an authorized published run.

Cross-cutting stabilization is a maintained architecture gate. A fixed-shape PostgreSQL fixture checks bounded query counts and local p95 latency through the same central-policy and workspace services used in production. The migration-cycle fixture reverses and reapplies the latest reversible domain and authorization-control-plane isolation migrations while retaining representative domain, authorization, archive, and audit state. Those tests run together with the permission/IDOR and raw runtime-role RLS matrices through `make test-stabilization`; `make test-certification` separately enforces model-boundary, policy-catalog, method-level denial, control-plane integrity, and RLS inventory contracts. Optimization never permits an unscoped query or authorization-result cache.

Reusable documentation has its own PostgreSQL certification composition. `make test-documentation-certification` combines the document/publication service and API corpus, malicious rendering boundary, complete authenticated-route and IDOR matrix, raw runtime-role forced-RLS checks, and the authorization-aware reference dataset with 2,500 immutable revisions. It introduces no parallel implementation contract: ADRs 0019 and 0021–0027, the normal migrations, the central permission inventory, and the forced-RLS inventory remain authoritative. The `0.3.0` claim is limited to the implemented one-MSP-per-installation documentation foundation and does not imply final capacity, hosted multi-MSP isolation, supported encrypted backup tooling, malware quarantine, or external legal-signature status.

Operational inventory and external credential references have a parallel PostgreSQL certification composition. `make test-inventory-certification` combines supplier catalogs, retained asset/publication provenance, hardware and software lifecycle, entitlements, contracts and protected costs, external credential pointers, hostile attachment handling, typed relationships, recovery, authenticated-route/IDOR, forced-RLS, migration, concurrency, and bounded reference-performance evidence. ADR 0020 and ADRs 0029–0038, normal migrations, the permission inventory, and forced-RLS inventory remain authoritative. The `0.4.0` claim is limited to the implemented one-MSP-per-installation operational foundation; it does not imply provider-item validation, customer-secret custody, cross-client reporting, a production malware-signature engine, hosted multi-MSP isolation, or final capacity.

Organization routes have an explicit in-context fallback: an unsupported nested path returns to that authorized organization's overview rather than silently changing to the MSP workspace. Missing or unauthorized workspaces retain one non-disclosing unavailable state. Browser coverage treats URL-derived workspace context, keyboard focus, history, stale-response cancellation, capability navigation, and denied-state accessibility as boundary behavior rather than cosmetic shell behavior.

Documents compose stable Markdown blocks through structured placement trees. Each placement resolves either the block's current revision (`live`) or one immutable revision (`pinned`); deterministic depth-first assembly is bounded by placement count and depth. MSP-owned documents may be projected into an organization's title-first Documentation listing through an explicit reference record without copying content or changing ownership. The placement/reference graph is also the backlink source of truth: bounded impact projections are filtered through the requesting member's exact workspace visibility and distinguish live, pinned, source, and listing audiences. Shared edits authorize against the block owner's scope and append an immutable revision; destination editors lacking that authority may atomically detach a non-primary placement into a destination-owned copy while preserving placement identity and descendants. Application and PostgreSQL guards reject foreign parents, invalid pins, sibling-client sources, and ancestor cycles. STATIC publication later resolves the same placement manifest to exact revisions before signing and rendering immutable artifacts.

Entity mentions remain portable Markdown links in the form `tekdocs://entity/{uuid}`. Search uses the same workspace-visible entity query as typed relationships. Rendering discards the authored label and substitutes server-authorized name/type/workspace metadata; an inaccessible or missing target becomes one generic unavailable reference, preventing stale labels from leaking hidden records.

Documents carry one portable built-in category and may be designated as reusable templates. Instantiation resolves the source placement graph, creates an independent destination-owned document, copies only active source-owned managed attachments under new Entity identities, and rewrites their stable `tekdocs://attachment/{uuid}` links. Managed attachment records retain the authored filename only as metadata; storage keys are opaque, file bytes never use a public media route, and downloads authorize through the exact visible owning document. `0.3.10` places replaceable storage and scanner interfaces in front of this path: bounded bytes enter an opaque quarantine key, conservative structural/content scanning runs, checksum-verified bytes promote to managed storage, and only then is a clean attachment record created. Rejection or failure removes storage remnants; download, template copy, and STATIC publication recheck clean status, size, and SHA-256. ZIP validation reads metadata without extraction and rejects traversal, links, encryption, nested archives, and bounded expansion/ratio violations. The built-in scanner is defense in depth, not a maintained external signature engine. UTF-8 Markdown import enters through normal document creation and immutable revision-one storage; export returns the deterministically resolved Markdown rather than editor HTML. ADRs 0024 and 0036 define the transfer and intake boundary.

Operational assets use the same typed `EntityLink` graph as other addressable records. Asset-focused discovery includes only `client_asset` Entities visible in the active MSP or exact organization Workspace; `related_to`, `depends_on`, and `references` retain the normal relationship read/create/archive permission and MFA boundary. Bounded asset mutation resolves and locks 1–100 unique Entity IDs before doing any work. Hardware state changes append normal lifecycle evidence, while archive is soft/recoverable and refuses software installations with active license coverage or seats. One transaction prevents partial success and makes guessed, stale, sibling, mixed, or dependency-blocked selections non-disclosing. ADR 0036 defines this batch contract.

STATIC publication creates a separate append-only `DocumentPublication`; it never changes the editable source. Publication locks the source graph, resolves every placement to an exact immutable block revision, resolves authorized entity cards and active source-owned attachments, and fails atomically when a dependency is unavailable. A versioned canonical JSON manifest and the retained canonical Markdown and sanitized HTML form one length-delimited snapshot payload. TekDocs stores its SHA-256 digest and an Ed25519 signature made with a deployment-supplied key, together with the public verification key and fingerprint needed for later validation. Each `v2` publication also retains a deterministic PDF and independent copies of referenced attachment bytes as append-only, checksummed artifacts whose descriptors are signed in the manifest. Reason, intended audience, and permanent or review-on-date retention are mandatory; review due, superseded, and current states are derived without mutating evidence. Corrections form a one-successor append-only chain. Publication and artifact downloads authorize through the source workspace, while forced RLS, scope/manifest guards, deferred artifact-set validation, and storage rollback backstop the application boundary. ADRs 0025 and 0026 define the snapshot and artifact lifecycle contracts.

## Trust boundaries

- Browser to same-origin Django session and CSRF boundary.
- MSP users to client-scoped data.
- Client portal users to explicitly published data.
- Application to encrypted secret provider.
- Workers to untrusted external integrations.
- Application to uploaded files and rendered Markdown/PDF.

Authorization is centralized and deny-by-default. Database scoping and constraints backstop application policies; they do not replace them.
