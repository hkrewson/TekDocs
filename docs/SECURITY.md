# Security Baseline

TekDocs targets the current OWASP ASVS Level 2 controls appropriate to a self-hosted business application.

## Non-negotiable controls

- Same-origin, HTTP-only, secure production session cookies with CSRF middleware enabled.
- Invite-only registration after a one-time owner bootstrap.
- The first-owner endpoint requires a high-entropy deployment secret, compares it in constant time, and transactionally locks a migration-created singleton installation record. The status endpoint exposes only whether bootstrap remains required.
- The browser reads the CSRF cookie established by `django-allauth` and sends it as `X-CSRFToken` for login and logout. Session cookies remain HTTP-only; the deployment token and password are never written to browser storage.
- Production mail requires Django's SMTP backend, a valid sender and host, paired credentials, one TLS mode, or an explicit plaintext-SMTP acknowledgement for a trusted private hop. The development Mailpit UI binds only to loopback and must not receive real customer data.
- Invitation management requires the applicable catalog permission and MFA. Raw invitation tokens use maintained high-entropy randomness, are delivered in URL fragments, stored only as digests, rotated on resend, cleared on expiry/revocation, and excluded from API responses and audit metadata.
- Invitation acceptance requires CSRF, consumes a locked invitation exactly once, creates identity and membership atomically, returns one unavailable state for invalid lifecycle conditions, and removes the browser URL fragment before account entry.
- Password recovery returns the same request state for known and unknown addresses, uses expiring single-use Django tokens in scrubbed URL fragments, requires CSRF for mutations, does not auto-login, and invalidates existing password-bound sessions.
- Active browser sessions use maintained allauth records, are listable only by their owner, and require CSRF for revocation. Login and recovery throttles share Valkey across web workers; authentication audits remain append-only and exclude credentials and client/session identifiers.
- TOTP is required for privileged owner actions. TOTP secrets and recovery seeds are envelope-encrypted with the deployment master key; recovery codes are shown only on generation, and sensitive MFA changes require recent password reauthentication. MFA values are excluded from logs, email, and append-only audit metadata.
- OIDC is optional, configuration-driven, and uses allauth's maintained discovery, state, callback, token, issuer, audience, and signature validation. Provider secrets and discovery internals are excluded from public configuration responses; only existing invited identities with a provider-verified matching email can authenticate.
- Central policy authorization with stable permission keys, documented built-in roles, centrally declared MFA requirements, fail-closed organization access modes, and cross-tenant/cross-client negative tests. Views and services do not authorize by role name; frontend visibility is never authoritative.
- A maintained certification inventory classifies every tenant-bearing model. Authorization control-plane rows outside RLS use fail-closed scoped managers and database guards that make tenant ownership immutable, require same-tenant relationship edges, and require invitation/administrative actors to be tenant members. The control plane includes immutable Workspace identities resolved before domain RLS binding. Runtime startup verifies that guard inventory. This boundary is certified only for the supported one-MSP-per-installation topology.
- Additive custom roles may target the tenant, one organization, or a maintained access collection, but never bypass assigned-client reachability. MSP-private audience classification and cataloged sensitive-field projection remain hard constraints after role composition. Commercial cost rows are emitted only inside the `costs` member and that member is absent—not null, masked, counted, or summarized—without exact-scope `costs.view`; cost mutation also requires MFA-protected `assets.edit`.
- Recycle-bin reads and restores derive scope from the MSP or exact organization route. Restore requires the central recovery permission, the domain's archive/manage permission, MFA, and CSRF; stale, foreign, sibling, and guessed identifiers do not disclose records.
- Audit evidence is insert-only at both the Django model and PostgreSQL layers. PostgreSQL rejects row updates and deletes; the application exposes no retention bypass. Destructive table/schema administration remains inside the trusted database-owner boundary.
- Schema ownership is isolated to the one-shot migration service. Web, worker, and scheduler processes use a fixed non-owner/non-`BYPASSRLS` PostgreSQL role, validate the expected forced-RLS inventory at startup, and bind tenant/Workspace/organization scope only inside transactions. Missing scope, cross-scope writes, runtime unrestricted mode, and schema changes fail closed.
- Canonical Markdown with no executable raw HTML, MDX, inline styles, or author CSS. Authenticated preview requires `documents.view`, normal CSRF/session protection, and bounded input; server rendering uses a raw-HTML-disabled parser plus explicit `nh3` tag/attribute/scheme allowlists, followed by an explicit DOMPurify allowlist at the single browser HTML sink. A malicious corpus checks authored tags, active unsafe URLs, style/event attributes, and representative MDX payloads.
- Structured document placements keep transclusion outside the Markdown dialect. Live and pinned targets, parent scope, source visibility, ancestor-cycle rejection, MSP-reference dependency retention, and detached replacement scope are enforced in both the service and PostgreSQL layers; resolution and reuse-impact output are bounded. Backlinks expose only documents and client listings the requesting member can already view. Shared edits re-authorize the block owner's scope, while detach requires destination edit authority and never changes the source block.
- Entity mentions store only stable `tekdocs://entity/{uuid}` links. Search and render resolution use exact workspace visibility; authored labels are never trusted for display, and hidden/missing targets collapse to a generic unavailable card. Raw HTML, active URLs, and unsanitized rendered output remain prohibited.
- Managed document attachments store opaque provider keys and stable `tekdocs://attachment/{uuid}` references, never public media URLs. Replaceable storage/scanner adapters place bounded bytes in opaque quarantine, run conservative executable/polyglot, AV-test-marker, active-PDF, image-container, text-control, and ZIP metadata checks, then promote only checksum-verified clean bytes. Rejection, scanner/provider failure, integrity mismatch, or database rollback deletes remnants and creates no downloadable record. Clean status plus provider/engine/time are retained; download, template copy, and STATIC reads recheck size and SHA-256. ZIPs are never extracted and reject traversal, encryption, symlinks, nested archives, excessive members, expansion, and compression ratio. Exact document authorization, forced-download disposition, `nosniff`, private caching, soft removal, PostgreSQL scope guards, and forced RLS remain mandatory. The built-in scanner is not claimed as equivalent to a maintained external malware-signature engine. Markdown import is UTF-8 `.md` only and bounded to 1 MiB; export contains resolved Markdown but never attachment bytes.
- Asset relationships reuse the typed EntityLink policy/RLS boundary and exact active Workspace visibility; client asset search cannot discover sibling records. Bulk asset mutation requires MFA-protected `assets.edit`, accepts at most 100 unique IDs, locks the complete exact-scope set before changing it, runs in one transaction, appends normal lifecycle/audit evidence, and returns one non-disclosing failure for stale or foreign selections. Bulk disposal is prohibited; recoverable archive rejects software installations with active license coverage or seats.
- STATIC publication runs only in the source document's owning workspace and freezes exact authorized block revisions, entity projections, and source-owned attachment bytes into a versioned canonical manifest. Missing or foreign dependencies fail atomically. Canonical Markdown, sanitized HTML, and manifest bytes use an unambiguous length-delimited snapshot format whose SHA-256 digest is signed with Ed25519. The private key is deployment-supplied and never returned or stored in PostgreSQL; retained publications contain only public verification material. New publications retain a deterministic PDF and independent attachment copies under opaque names; reads recheck signed sizes and SHA-256 checksums. Mandatory reason, intended audience, retention, and append-only correction metadata are signed. Django/PostgreSQL reject publication and artifact mutation, forced RLS preserves client isolation, deferred guards require a complete signed artifact set, and failed operations remove partially written bytes.
- Credential-reference records contain provider pointers only. Separate view, manage, and open permissions are scope-aware; list/search responses omit provider links, and the audited handoff revalidates the target before redirecting. Share links, arbitrary URLs, secret-shaped input fields, provider retrieval APIs, value proxying, and customer-secret storage are prohibited.
- Supplier catalogs exist only in vendor/manufacturer workspaces and use stable product/model identities plus immutable schema and model revisions. Specification schemas are closed, size/property bounded, and restricted to a maintained scalar/string-array vocabulary without remote references, authored regular expressions, compound evaluators, or executable extensions. Values are validated server-side; updates require the exact base revision. Central `assets.view`/`assets.edit` policy, exact workspace scope, database edge guards, append-only triggers, and forced RLS protect the catalog history.
- MSP/client asset creation accepts only an addressable active supplier model and derives every ownership/provenance field server-side. MSP ownership is the installation's one explicit MSP Workspace; `organization IS NULL` is only its guarded scope projection and never means all client organizations. The asset retains exact supplier/product/model/revision/specification identifiers, validated values, and a checksum; applicable documentation retains exact verified `client_visible` STATIC publications and digests in append-only rows. Database triggers reject Workspace/scope retargeting and provenance mutation. MSP/client-mode RLS adds read-only access to supplier catalog rows and only those STATIC publication/document/artifact rows explicitly associated with a product; unrelated supplier documents, client operational records in MSP mode, and every cross-scope write remain unavailable. Vendors is a grouped projection of retained supplier identity, never a label match or implicit relationship.
- Hardware lifecycle uses a hardware-only client-scoped current-state profile and an append-only typed event ledger. Serial/tag normalization, acquisition and warranty dates, exact-client active person/site/location assignments, terminal disposal, profile/event edges, event immutability, and forced RLS are enforced in both application services and PostgreSQL. Mutation audits and lifecycle events omit acquisition/warranty references, disposal reasons, and other free text.
- Software licensing uses a software-only client installation profile plus addressable product-bound entitlements. Exact-client/product installation links, seat limits, person/installation targets, renewal constraints, append-only value-minimized history, PostgreSQL guards, and forced RLS prevent cross-client assignment and history rewriting. License references are excluded from audit metadata; license keys and credential values are not accepted.
- Redacted structured logs, append-only audit records, scoped API/service credentials, and webhook replay protection.
- Customer credential values are not stored or retrieved by TekDocs. Credential records are strictly validated external references; 1Password unlock, authorization, reveal, and value audit remain in 1Password.
- Runtime deployment secrets resolve through one mutually exclusive direct-or-`*_FILE` reader. Production Compose mounts bounded, validated files only into the database/migration/runtime/auth service that needs them; the production rehearsal rejects ambiguity and checks container environments, image history, and logs for value leakage. An unclaimed installation is unready without its separately mounted bootstrap token, while a claimed installation permits permanent token removal. Direct environment compatibility remains development-only policy work to remove at `0.8.7`.
- SSRF-resistant outbound integration and monitoring requests.
- Dependency, license, secret, source, container, and browser security gates.
- Reviewed Python build/production/development hash locks, digest-pinned external images and local scanners, commit-SHA-pinned Actions, local workflow linting, and controlled Dependabot updates.
- A blocking PostgreSQL stabilization gate that combines bounded policy-aware query paths, representative migration reversal/reapplication, the complete authenticated-route and IDOR matrix, scoped custom-role composition, recovery, audit immutability, and raw non-owner RLS checks. Performance work may not cache or bypass authorization scope.
- A dedicated PostgreSQL documentation-certification gate that composes document/publication behavior, hostile rendering, the complete authenticated-route and IDOR matrix, raw non-owner RLS checks, and the authorization-aware 2,500-revision reference fixture. It supplements rather than replaces browser, security, production-image, upgrade, and database/media recovery evidence.
- A dedicated PostgreSQL inventory-certification gate that composes supplier catalogs, retained asset provenance, hardware/software lifecycle, entitlements, contracts/cost projection, credential references, hostile attachments, typed relationships, recovery, the complete authenticated-route and IDOR matrix, raw non-owner RLS checks, migrations, concurrency, and the authorization-aware inventory reference fixture. It supplements rather than replaces browser, security, production-image, upgrade, and database/media recovery evidence.
- Keyboard and axe regression coverage for implemented MSP/client workflows, unavailable and capability-denied states, direct routes, history, mobile context changes, and stale workspace responses across the release browser matrix.

Production startup must fail for missing or placeholder secrets, wildcard hosts/origins, insecure cookies, inadequate HSTS, mismatched public/CSRF origins, incomplete OIDC settings, debug mode, or an unsupported database configuration. The development Compose stack's HTTP origin requires the explicit localhost-only insecure-public-URL acknowledgement.

See `docs/THREAT_MODEL.md` for the initial abuse analysis. Security reports are handled according to root `SECURITY.md` once the public repository is published.

## Inventory and external-reference certification

Operational collection pagination is never an authorization mechanism. TekDocs resolves the exact MSP or organization Workspace and central permission before applying a bounded page; count and continuation metadata therefore describe only that authorized Workspace. Cost-denied contract responses omit the complete protected member, and list/search responses never contain 1Password Private Links. Provider handoff remains a separately authorized redirect with value-free audit metadata, and the interface tells operators to replace a stale pointer rather than implying that TekDocs validated the provider item.

The `0.4.0` inventory certification runs on PostgreSQL and combines supplier catalogs, competing seat allocations, immutable provenance recovery, CSV/bulk rollback, archived-pointer denial, hostile attachment handling, typed relationships, cross-Workspace IDOR, forced RLS, bounded reference performance, migration state, and clean `0.3.12` upgrade/restore rehearsals. This does not turn the structural attachment scanner into an external signature engine or make the host/container administrator untrusted.

Network placement added in `0.4.1` remains inside the same exact-Workspace and central-policy boundary. Site, location, rack, and optional hardware-asset edges are revalidated in PostgreSQL; rack occupancy uses both service row locks and a transaction advisory lock before overlap checks. MSP network routes select only MSP-owned rows and are not cross-client reports. Recovery, bulk transfer, and final network scale certification remain assigned to later network milestones.

Network addressing added in `0.4.2` applies the same boundary to VRFs, VLANs, and subnets. The default routing table and each VRF are separate overlap namespaces. CIDR canonical form, derived family, VLAN bounds, same-Workspace ownership edges, and overlap are enforced in both the service and PostgreSQL; advisory locks prevent concurrent check-then-insert races. A VLAN is not treated as a routing-isolation boundary.
