# 1.0.0 candidate: Git-backed compatibility boundary

Prepared November 13, 2026 from deployed v0.9.19. Preparation baseline:
`5e63b391f7a12c0b9df127e6de05f8b9f4fcf958`.

This packet prepares, but does not yet accept or publish, the first 1.0
candidate. It freezes the intended version and compatibility boundary for the
Git-backed Markdown content graph and the supported clean-start workflows.
Pushing, tagging, image publication, deployment, production data changes and
the final release decision remain separately controlled.

## Candidate scope

- Git-backed documents and reusable fragments are canonical for new content,
  with accepted commits, deterministic indexes, explicit conflict handling and
  independent recovery.
- Supported clean-start workflows cover native discovery/export, publication,
  primary-file versions, keys and entity references, diagrams, templates and
  monitored sources, including client isolation and negative access states.
- Existing legacy data, signed publications, PDFs and file versions remain
  preserved. Six automatic legacy-migration shapes remain deferred and are not
  1.0 dependencies.
- Selected existing documents are recreated manually after reviewed private
  copies. This does not transfer legacy identity, history, access, references or
  publication authority automatically.
- The broad interface redesign remains the first post-1.0 priority. Functional
  accessibility or workflow defects found during candidate acceptance still
  block this release.

## Release notes

- Establish the supported Git-backed Markdown content graph and repository
  authoring boundary delivered through the 0.9.x transition line.
- Include native document lifecycle, reuse, publishing, retained files,
  configuration and recovery paths validated in the combined clean-start lane.
- Preserve explicit Workspace, organization, client, audience, RLS and portal
  isolation across repository content and retained operational records.
- Retain normal schema-only upgrades. Installation or upgrade does not copy,
  promote, delete or change authority for existing documents.
- Retain immutable publication evidence, signed artifacts, PDFs and managed-file
  custody across supported upgrade, rollback-refusal and recovery paths.

## Current evidence

Exact source `03abebfe9653349bd3f2f2ce7aa14da83cc15ec4` passed Build
43139510245's complete release lane: all PostgreSQL shards, the combined
clean-start browser journey, five browser configurations, supported upgrades,
independent encrypted recovery, production images, SBOM and vulnerability
checks, DAST, performance, both CodeQL languages and final validation. Commit
`5e63b391` reconciled that evidence without changing runtime source.

The maintainer reviewed private copies of the three accessible production
documents. The Setup guide was already Git-backed. The selected UniFi guide was
recreated through repository authoring and verified at indexed commit
`861c6eaf8fc7`; both editable duplicates were then archived recoverably. The
smoke-test document was intentionally not recreated. This is production workflow
evidence, not candidate CI, automatic migration proof or a release decision.

Local candidate preparation reused the existing `tekdocs` Compose project. The
backend, frontend, worker and scheduler were rebuilt in place at 1.0.0; service
health, Django system and migration-drift checks, checked-in OpenAPI generation,
Ruff, mypy, repository script tests, product/Wiki/Compose contracts, production
setup and restore contracts, version agreement and the frontend production build
passed. The source-secret scan exposed five stale exact-line exclusions for four
unchanged permission-route names and one browser preference key. Each match was
reviewed, only those fingerprints were advanced, and the full Git-visible source
scan then passed inside the existing backend service. A frontend helper was
mistakenly invoked before inspection and used an isolated pinned-Node container
because the host patch version differed; its successful test/verify result is
supplementary and is not acceptance evidence. The hosted exact-candidate lane
remains required.

The commit-matched review of preparation source `59fdcb82` covered all 151
changed files and reported one low finding: any installation member could send
enough overlapping caller-supplied Mermaid previews to occupy the shared
eight-job renderer pool. The endpoint intentionally remains membership-scoped:
it reads no stored document and is used by client-facing authorized document
views. The follow-up candidate instead reserves at most two active renderer jobs
per tenant/user principal with PostgreSQL session advisory locks, releases them
after success or failure, and relies on database-session closure after a worker
failure rather than an expiring lease.
The regression reproduced three simultaneous requests entering the renderer
before the change; afterward the third receives 429 while the first two complete.
The complete rendering module, cross-connection PostgreSQL reservation/release
coverage, Ruff, mypy and generated OpenAPI agreement pass. This disposes the
reported impact in source, but a new commit-matched review must verify the
follow-up candidate before acceptance.

## Open acceptance gates

1. Run the complete hosted release lane against the exact final candidate
   commit. Historical `03abebfe` evidence cannot certify later version or record
   changes.
2. Complete a fresh commit-matched automated or AI-assisted security review of
   the renderer-capacity follow-up and explicitly disposition every current
   finding. The preparation-candidate review is retained as historical evidence,
   not relabeled as follow-up acceptance. TekDocs does not claim an independent
   human assessment, penetration test, compliance audit, certification or
   independent assurance.
3. Complete the maintained human desktop-keyboard, touch/mobile, screen-reader
   and 200% zoom walkthroughs for Assets, Contracts, Networks and Documentation
   and Files. Automated browser passes do not substitute for these checks.
4. Investigate or explicitly disposition the retained recurring-template and
   WebKit dialog timing failures before aggregate acceptance.
5. Reconcile the public Wiki drafts and final support/release statements without
   claiming comprehensive automatic legacy migration.
6. Record the maintainer's risk decision, 1.0 release decision and compatibility
   freeze. Until then this packet remains **prepared, not accepted**.

## Local execution boundary

Local validation must reuse the existing `tekdocs` Compose project. The full
`release-gate` provisions additional projects, databases or volumes through
several rehearsals, so those gates remain hosted unless the maintainer separately
authorizes that local exception. No such exception is part of this preparation.
