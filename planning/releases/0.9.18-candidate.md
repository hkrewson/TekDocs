# 0.9.18 candidate: client-published document migration

Prepared November 1, 2026 on main after published v0.9.17
(`835c4ff4df7074ff4acec635a770f94bcde2100b`). Preparation baseline:
`6963608bc36db78953aeb2fd568903c9ded5d7cd`. The maintainer authorizes direct-main
commit/push and automatic image, application-tag and updater-receipt delivery.
Production deployment, live-data migration and Wiki publication remain separate.

## Release notes

- Migrate supported documents with existing client-visible publications without
  replacing their client links, signed manifests, signatures, approval history,
  retained PDFs or managed-file versions.
- Preserve MSP-only and client-only section profiles and nested narrowing. New
  Git-backed publications freeze the selected audience's verified composition;
  client snapshots exclude staff-only sections, ordinary-file references and
  unused field-key bindings. All primary-file versions remain retained.
- Publish promoted organization documents for clients through the existing
  interface, including review-on-date retention. Independent authorized approval
  is required before portal availability. A correction keeps its predecessor's
  audience, and withdrawal never reopens an older superseded publication.
- Preserve portal list/detail/download behavior, current client authorization,
  notification identities and authorized targets through migration, correction,
  withdrawal, authority rollback and re-promotion.
- Bind database insertion guards to the selected audience and retained file/key
  evidence. Corrupt source variants, stale migration previews, damaged PDFs,
  invalid audience certificates and unauthorized writes fail without partial state.
- Extend real browser/server, runtime-role isolation, fresh/0.8.46 upgrade and
  independent encrypted-restore cohorts. Reconcile the older mocked browser
  contract with enabled new-publication controls while keeping correction audience
  locked and preserving original lifecycle, denial, PDF and accessibility checks.
- Preserve every timestamp microsecond in client upgrade/recovery fingerprints.
  Fresh review reproduced a one-microsecond notification-history change producing
  the same prior digest; the strengthened proof distinguishes that change without
  modifying application storage or signed artifacts.
- Include post-0.9.17 failure-only worker/browser diagnostics and the reproduced
  publication-server lifetime correction. The shared finite suite budget preserves
  existing per-case limits and zero retries for the real publication journey.
  Earlier unexplained notification/browser failures remain investigation obligations.

This release packages reviewed development work. Preparation changes version metadata and documentation and strengthens recovery
fingerprints to retain full timestamp precision. It adds no new dependency, API
field or application runtime behavior beyond that accumulated delta. Normal Django migration 0212 installs the
new publication guard. Upgrading applies schema migrations; copying/promoting
existing documents remains an explicit reviewed operator action. Existing signed
artifacts are verified from retained bytes, never regenerated to establish parity.

General cross-Workspace reuse, repeated legacy block occurrences, unsupported or
damaged history, broader structural changes and aggregate 1.0 acceptance remain
outside this bounded checkpoint. Migrated DocumentPublication delivery remains
distinct from repository-native RepositoryStaticPublication delivery.
