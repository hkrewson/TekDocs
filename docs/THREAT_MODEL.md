# Initial Threat Model

## Protected data

Client documentation, credential-reference metadata, personal/contact information, asset and network inventory, vendor terms and costs, audit history, integration credentials, compliance evidence, and immutable publications. Customer credential values are deliberately outside the TekDocs trust boundary.

## Principal threats and planned controls

API-token threats include bearer theft, plaintext retention, guessed-prefix enumeration, scope confusion between MSP and client Workspaces, permission drift, service-account interactive login, stale credentials, and token use to mint broader tokens. Mitigations are header-only transport over TLS, high-entropy one-time material with password-hash-only storage, generic authentication failures with dummy-hash work, exact Workspace plus central-policy permission intersection, non-interactive read-only service subjects, mandatory bounded expiry, immediate rotation/revocation, session/MFA/recent-reauthentication management, value-free audits, forced RLS, and PostgreSQL authority guards. Client custody and bearer replay until lifecycle termination remain inherent residual risks tracked as `TD-RISK-046`.

| Threat | Initial controls |
| --- | --- |
| Missing or orphaned owner identity | Every Entity has a non-null immutable MSP/organization Workspace owner. There is exactly one MSP Workspace per installation tenant and one Workspace per organization; PostgreSQL rejects mismatched tenant/Workspace/organization edges, and ordinary Entity creation without an owner fails. Organization archival retains its identity and owned records, while protected immutable Workspace relationships prohibit physical deletion from orphaning data. `Tenant` remains only the one-MSP installation/future-hosting boundary; hosted multi-MSP control-plane safety is not claimed. |
| Cross-client or cross-tenant access | Explicit ownership columns, fail-closed scoped query APIs, same-tenant database triggers, central permission-key policy, and forced RLS on implemented core tenant data under a fixed non-owner/non-`BYPASSRLS` runtime role. Transaction-local request/job scope denies missing, cross-tenant, sibling-client, write-check, pooled-connection, and runtime `all`-mode bypasses. Organization access modes can only narrow role permissions; `assigned_only` requires the owner or an explicit same-tenant membership assignment. Collection-scoped grants apply only to active members and cannot create that assignment. Lists, switchers, direct routes, domain APIs, searches, and backlinks share the policy-filtered boundary and a blocking negative-isolation/IDOR matrix. The `0.2.0` inventory classifies every tenant-bearing model; control-plane rows outside RLS have immutable ownership, same-tenant edges/actors, scoped managers, central-policy API isolation, and migration-cycle tests. This boundary is certified for one MSP per installation; hosted multi-MSP identity/control-plane isolation remains a future architecture review. |
| Privilege escalation through role or client-mode administration | Owner identity cannot be reassigned, tenant memberships accept only tenant-scoped built-in roles, and role/mode/assignment/collection mutations require catalog permissions plus TOTP and CSRF. Custom permissions have a reviewed database-backed ceiling; submitted role metadata is ignored, targets are tenant-scoped, and audit events contain no role, organization, or collection values. Guessed member/client/collection identifiers return non-disclosing failures. |
| MSP-private or sensitive-field disclosure | Entity audience defaults to MSP private and client projection requires explicit client visibility plus exact organization ownership. Audience constraints apply after role evaluation. Commercial costs are a separate exact-client relation projected through the maintained policy catalog: the entire `costs` member is absent when denied, list/search never queries financial values, and no totals/counts become an oracle. `costs.view` does not imply mutation, secrets, or other sensitive-data access. |
| Assignment mistaken for authorization | Staff assignments target tenant memberships rather than Person names, job titles, or email strings. PostgreSQL rejects cross-tenant assignment edges; the policy service separately requires the requested permission and MFA. Adding or removing an assignment is owner-permission, TOTP, and CSRF protected, idempotent, and value-free in audit metadata. |
| Stale or forged workspace context | Workspace identity is explicit in URLs and API scope, is resolved through tenant and policy boundaries on every request, and never grants access by selection alone. Scope changes clear stale data before loading, creation derives ownership server-side, parallel tabs remain independent, and browser tests assert that responses from a prior workspace cannot appear after a switch. |
| MSP operational scope mistaken for tenant-wide aggregation | The MSP owns operational records without being a synthetic client. Its data scope resolves the installation tenant's one explicit MSP Workspace; `organization IS NULL` is only the guarded projection of that owner and never means every organization in the tenant. Separate MSP and organization routes resolve one Workspace before policy evaluation; scoped managers, PostgreSQL ownership guards, forced RLS, and two-way negative IDOR tests prevent client records appearing in MSP inventory or MSP records appearing in a client. Cross-client reporting requires a future explicit projection and permission design. |
| Performance optimization bypasses authorization | Query budgets wrap the central policy and exact-workspace services rather than an unscoped repository. The reference dataset grows unrelated tenant/client data while permission, IDOR, audience, sensitive-field, recovery, audit, and raw runtime-role tests run in the same blocking stabilization gate. Authorization results and scoped querysets are not shared across users, tenants, organizations, or requests. |
| Migration weakens isolation or loses authorization state | A PostgreSQL migration-cycle fixture preserves representative identifiers, ownership, custom-field versions, links, scoped-role assignments, archived state, and audit evidence across reversal/reapplication of the latest isolation migration. Forced-RLS inventory, runtime-role restrictions, clean installation, and the supported upgrade path are independent blocking checks. |
| Unauthorized or over-broad recovery | Recycle-bin discovery is exact-workspace scoped and requires both recovery visibility and domain read access. Restore composes recovery plus domain mutation permissions, MFA, CSRF, reachability, dependency checks, row locks, and one transaction. Exact archive timestamps prevent parent restoration from reviving records archived by an earlier action. |
| Audit evidence alteration | Django rejects instance mutation and PostgreSQL rejects row update/delete, including ORM bulk and raw-SQL attempts. No application retention endpoint exists; destructive table/schema administration remains in the trusted database-owner boundary. |
| Account takeover | Maintained authentication library, invite-only onboarding, MFA, rate limits, session inventory/revocation, secure recovery. |
| Email disclosure, delivery interception, or queued-message oracle | Central fixed templates, send-time authorization/preferences, no retained destination or rendered copy, safe failure codes, header validation, bounded SMTP timeout/retry, TLS-by-default production validation, paired credentials, loopback-only development inbox, and no message contents in command output. |
| Invitation theft, replay, or enumeration | Owner-only issuance, 256-bit random tokens, digest-only storage, constant-time matching, fragment-based delivery links and immediate browser scrubbing, CSRF-protected transactional acceptance, expiry, resend rotation, revocation, generic unavailable/delivery failures, and value-free audit events. |
| Client session crosses into the MSP surface or another client | Client invitations bind one immutable active-client organization. Authenticated context selects a separate portal shell; the central MSP permission service rejects client roles; portal APIs derive scope from membership rather than route input. Database guards reject cross-tenant/non-client edges and organization retargeting. MSP sessions are rejected from portal endpoints, and client sessions are rejected from organization discovery and ordinary domain routes. |
| Client-visible STATIC content carries an MSP-private entity projection | New approval rejects referenced entities unless they are client-visible and owned by the exact client. Portal reads repeat that check and omit unsafe historical snapshots without altering evidence. Retained HTML receives a second browser sanitization pass. |
| Notification work is lost, duplicated, crosses tenants, or persists sensitive values | Invitation and publication transitions enqueue fixed-schema events in the same transaction. Tenant-scoped idempotency keys, immutable event payloads, forced RLS, bounded claims, append-only consumer receipts, stale-claim recovery, exponential retries, and dead-letter state provide recoverable, idempotent consumption. Inbox projection retains only immutable recipient edges; current permission, exact-client membership, organization access, surface, source lifecycle, and reference safety are checked before fixed display copy or typed navigation is returned. Withdrawn client material is generic and non-linking. Cross-surface/recipient IDs fail closed, read state is CSRF protected, and PostgreSQL rejects retargeting or deletion. |
| Controlled client subsystems pass separately but fail when composed | The `0.6.0` certification gate composes identity, publication decisions, portal projection, outbox, inbox, SMTP, preferences, administration, signed histories, permission/IDOR, forced RLS, migration, scale, browser, upgrade, and restore evidence. The real browser path uses distinct publisher, MFA approver, and exact-client sessions so a mocked or same-actor shortcut cannot satisfy the release boundary. |
| API typo, error detail, or retry semantics becomes a disclosure or duplicate-write boundary | Public collection filters are explicit and strict, pagination is bounded after authorization, generic errors expose stable value-minimized copy plus a correlation UUID, and idempotency is declared only for naturally convergent operations. Generated-client drift is blocking. Durable request fingerprints/result replay and explicit collision-free operation IDs remain mandatory before integration certification. |
| Stored XSS or interface spoofing through Markdown | No raw HTML/MDX/author CSS, bounded authenticated preview, raw-HTML-disabled parsing, explicit server tag/attribute/URL-scheme allowlists, a second browser allowlist at one centralized HTML sink, CSP, and a parsed-DOM malicious corpus. Semantic highlight and callout presentation are application-controlled rather than arbitrary user styles. |
| Malicious file upload, attachment disclosure, or transfer confusion | Managed files use replaceable provider/scanner adapters, opaque quarantine and managed keys outside public media routing, stable UUID records, exact tenant/workspace/document ownership, forced RLS, and central-policy download checks. Only scanner-clean, checksum-promoted bytes become records; failures delete remnants. The hostile corpus rejects executable/polyglot signatures, the standard AV test marker, active PDFs, malformed images, unsafe text controls, and ZIP traversal/encryption/links/nesting/member/expansion/ratio abuse without extraction. Reads recheck clean status, size, and SHA-256 and return forced-download/private/`nosniff` responses. The built-in scanner is defense in depth rather than a maintained external signature engine. Template instantiation copies only verified active source attachments under new identities and fails closed for foreign references. Markdown import accepts bounded UTF-8 `.md`; export contains resolved Markdown references but no private file bytes. |
| Bulk asset mutation crosses scope or commits partially | Bulk requests accept 1–100 unique stable IDs and resolve plus lock the complete exact Workspace set before one transaction mutates anything. Central `assets.edit` and MFA apply before input processing; stale, duplicate, guessed, sibling, mixed-kind, disposed, or dependency-blocked selections return one bounded failure and roll back. Hardware state changes append normal lifecycle/audit rows. Archive is recoverable and refuses software with active license coverage or seats. Asset relationships separately reuse relationship permissions and exact-workspace Entity search/backlinks. |
| CSV import/export leaks data or commits forged rows | Asset CSV uses one versioned exact-header allowlist rather than model serialization. Export resolves one authorized Workspace, excludes credentials, costs, contracts, licenses, attachments, assignments, disposal, and provenance payloads, and escapes formula-shaped cells. Import bounds bytes/rows/cells, validates UTF-8 and structure, rejects foreign IDs and duplicate identifiers, requires MFA/CSRF `assets.edit`, binds dry run to the exact file and Workspace with a short-lived signed token, reparses at apply, derives retry-safe identities from Workspace plus import key, and commits the whole file in one transaction. |
| Unbounded or unstable inventory collection | Asset, license, contract, and credential-reference reads authorize one exact Workspace before applying a stable page of at most 100 rows. Exact counts describe only that scope. A combined PostgreSQL fixture fixes page size, whole-request query ceilings, and local p95 latency so per-row authorization/provenance regressions fail; MSP pages remain explicitly non-aggregate. |
| Forged or conflicting network placement | Racks and devices are stable exact-Workspace Entities. Site, location, rack, and optional hardware-asset targets are selected inside the resolved Workspace and revalidated by PostgreSQL, including active/hardware requirements. Device placement locks the rack in the service and takes a transaction-scoped advisory lock in PostgreSQL before checking bounded contiguous units, preventing concurrent overlap. Rack moves/shrinks fail while they contradict placed devices. Logical links use the existing permission-filtered EntityLink boundary; MSP routes cannot aggregate client devices. |
| Forged or conflicting network address space | VRFs, VLANs, and subnets are stable exact-Workspace Entities. CIDRs must be canonical IPv4/IPv6 networks with server-derived family; VLAN IDs are bounded and Workspace-unique. The default table and each VRF are separate overlap namespaces. Service and PostgreSQL advisory locks serialize writes, and database guards reject malformed/noncanonical CIDR, family mismatch, foreign VRF/VLAN edges, and direct or concurrent overlap. Reusing a prefix in a different VRF is deliberate; assigning a VLAN does not bypass the routing overlap rule. |
| Forged wireless or DNS inventory | Wireless networks and DNS zones/records are stable exact-Workspace Entities under central `networks.view`/`networks.edit` policy, scoped managers, forced RLS, and database edge guards. SSIDs are bounded to the protocol's UTF-8 byte limit and may reference only same-Workspace sites, VLANs, and subnets. DNS names and type-specific values are canonicalized and constrained; CNAME conflicts, foreign zone/IP references, and concurrent conflicting writes are rejected. DNS values are omitted from broad Entity labels and audit metadata. Wireless credentials remain outside this subsystem and password-shaped API fields fail closed. |
| Forged circuit, contract, or handoff edge | Circuit and handoff records resolve one exact MSP or organization Workspace before central policy. Providers must be eligible same-tenant organizations; contracts must match provider and Workspace; site/location/device/interface placements must remain internally consistent. Strict serializers, scoped managers, advisory locks, forced RLS, uniqueness constraints, and database triggers reject unknown fields, sibling-client identifiers, direct-write forgery, contradictory placement, and interface reuse. Contract projections require `assets.view`, omit costs entirely, and linked contracts cannot be archived. |
| NetBox identity mapping becomes a cross-client oracle or unsafe sync authority | References resolve one exact Workspace before central `networks.view` or MFA-backed `networks.edit`, carry an explicit Workspace foreign key, and are revalidated by PostgreSQL under forced RLS. Only six reviewed content types, a positive numeric ID, and an optional SHA-256 fingerprint are accepted. A 500-item deterministic preview stores no arbitrary remote payload and performs no mutation or outbound request. TekDocs has no NetBox token, URL, job, automatic conflict resolution, or write-back in this slice. |
| Network search/export leaks client or sensitive data | Search and export resolve one explicit MSP or organization Workspace and central `networks.view` before querying. Bounded stable search returns no matched field. CSV uses a fixed versioned schema/family allowlist, spreadsheet escaping, batched iteration, private/no-store headers, and explicit exclusion of credentials, financial/contract details, asset-only data, provider payloads, and NetBox fingerprints. Sibling/MSP/anonymous IDOR, scale, upgrade, and restore tests are blocking. |
| Certified network boundary drifts toward an unsafe source of truth | The `0.5.0` certification gate keeps the supported boundary lightweight and exact-Workspace: devices extend hardware assets; VLAN, subnet, direct IP/MAC, wireless, DNS, circuit, and provider records remain documentation rather than live control; and NetBox support remains identity plus non-mutating preview. Retained Interface/VRF rows are compatibility data, not an ordinary authoring surface. Every later network change must extend the named certification gate and reconsider `TD-RISK-031` through `TD-RISK-038`; connector authority, secrets, discovery, monitoring, write-back, and cross-client aggregation require separate threat reviews. |
| Forged circuit, contract, or handoff edge | Circuit and handoff records resolve one exact MSP or organization Workspace before central policy. Providers must be eligible same-tenant organizations; contracts must match provider and Workspace; site/location/device/interface placements must remain internally consistent. Strict serializers, scoped managers, advisory locks, forced RLS, uniqueness constraints, and database triggers reject unknown fields, sibling-client identifiers, direct-write forgery, contradictory placement, and interface reuse. Contract projections require `assets.view`, omit costs entirely, and linked contracts cannot be archived. |
| Credential disclosure | Customer values remain in the external provider. TekDocs accepts only a provider-specific Private Link pointer, omits it from list/search responses, rejects secret-shaped fields and public share/arbitrary links, scopes view/manage/open independently, and records empty-metadata handoff audits. Archived pointers cannot be listed or opened. TekDocs cannot verify item existence or vault access; stale guidance requires a newly copied Private Link. The stored pointer remains sensitive metadata and a compromised host can exfiltrate it, but 1Password independently requires vault access and unlock before reveal. |
| Catalog schema abuse or provenance forgery | Catalog ownership requires an active vendor/manufacturer classification in addition to central asset permissions. Every product, model, schema definition/version, and model revision carries exact tenant/supplier scope under scoped managers, database edge guards, and forced RLS. Specification schemas are bounded closed objects using a maintained non-executable vocabulary; remote references, authored regex, compound evaluation, unknown keys, and oversized property/choice sets fail before validation. MSP/client assets retain exact supplier/product/model/revision/version identifiers, validated values, and a checksum rather than labels. Applicable document rows retain only verified client-visible STATIC publications and exact digests. Provenance columns and document rows are database-immutable; narrow read-only RLS projections expose associated catalog/publication data to the active operational workflow without exposing ordinary supplier documents, client operational data in MSP scope, or allowing supplier-scope writes. |
| Hardware lifecycle or custody forgery | Hardware-only current-state profiles derive scope from retained MSP/client assets. Server-selected person associations, sites, and locations must be active and belong to that exact workspace; sibling and guessed targets return unavailable states. Each locked mutation updates current state and appends a typed, value-minimized event in one transaction. Forced RLS and null-safe database guards reject cross-scope targets and unnormalized identifiers, event update/delete, profile deletion, invalid disposal state, and every post-disposal mutation. Sensitive references and reasons remain absent from lifecycle events and audit metadata. |
| Software entitlement over-allocation or relationship forgery | Software-only installation profiles derive scope and product identity from retained MSP/client assets. Licenses retain that supplier/product relationship; covered installations must match the exact workspace and product, while people and sites must belong to the same active workspace scope. Seat assignment locks the license and enforces its active limit before inserting a retained allocation. Value-minimized append-only events, null-safe database edge guards, forced RLS, and MSP/client/sibling/cross-tenant IDOR checks prevent history rewrites and forged relationships. License keys are never accepted, and renewal references remain absent from audits and events. |
| Runtime secret disclosure | Sensitive settings accept one direct or file source, never both. Production overlays use service-scoped read-only mounts below `/run/secrets`; files are root/application-owned, bounded, single-value UTF-8, and constrained to an approved root. Invalid source, path, type, mode, size, encoding, or ambiguity fails without printing values or host paths. The production rehearsal scans container environments, image history, and logs, and keeps the operator's 1Password session/token outside Compose and all application containers. Direct environment fallback remains available until mandatory production enforcement in `0.8.7`; host root and container-engine administrators remain trusted and can read mounted runtime material. |
| Malicious integration target | Address validation, private/reserved network blocking, redirect revalidation, time/size limits, signed webhooks, replay cache. |
| Destructive, forged, or prematurely distributed document change | Append-only block revisions are protected by application rejection and PostgreSQL triggers, content receives server-calculated SHA-256 checksums, parent/sequence/workspace edges are database-validated, and every update supplies its exact base revision. A stale base returns `409` with the authorized current revision and a bounded line diff without overwriting the submitted browser draft. Live/pinned placement trees resolve deterministically under count/depth limits; application and PostgreSQL checks reject invalid pins, foreign parents, sibling-client sources, and recursive block cycles. MSP-to-client transclusion requires an active listing reference, and that authorization edge cannot be removed while a dependent placement exists. Reuse impact is derived from that graph and permission-filtered; shared edits authorize the source block scope, while destination-authorized detach copies the resolved immutable revision and leaves the source untouched. Entity mentions ignore authored labels and resolve only through the viewer's workspace, collapsing hidden targets to a generic state. STATIC publication resolves exact dependencies under locks, signs a canonical snapshot digest with a deployment-held Ed25519 key, and retains deterministic PDF and attachment artifacts whose signed size/checksum is revalidated on read. Distribution uses a separate append-only decision ledger: client-visible approval requires a distinct MFA-reauthenticated authorized actor, withdrawal preserves evidence, and audience projections deny pending/withdrawn/superseded material. Central policy, non-disclosing lookups, advisory locks, forced RLS, and PostgreSQL event/order/scope/one-successor guards prevent a label or concurrent decision from becoming accidental portal authority. |
| Supply-chain compromise | Hash-locked Python/build dependencies, npm lockfile, digest-pinned runtime/tool images, commit-SHA-pinned Actions, Dependabot, dependency review, CodeQL, Gitleaks, Trivy, SBOM, and later release provenance attestations. Hosted controls are not represented as verified before an observed authorized run. |
| Backup loss or key loss | Documented encrypted backup, restore rehearsal, separately protected wrapping/signing keys, explicit recovery checks. |

This model must be revised when authentication, RBAC, secret storage, uploads, rendering, client access, or external network behavior changes.
