# Security Baseline

TekDocs targets the current OWASP ASVS Level 2 controls appropriate to a self-hosted business application.

## Non-negotiable controls

Public API inputs use explicit serializers and bounded pages; declared filter sets reject unknown parameters so a spelling mistake cannot silently widen a query. Authorization and exact Workspace selection precede filtering, counting, and pagination. Framework errors return stable value-minimized messages with a server correlation UUID rather than exception text, SQL details, identifiers, or secrets. `Idempotency-Key` is a bounded opaque value and is documented only where the operation is naturally convergent; it is not represented as durable replay storage. OpenAPI operations use stable unique scope/list/detail identifiers and the generated TypeScript client is a checked artifact.

- Same-origin, HTTP-only, secure production session cookies with CSRF middleware enabled.
- Invite-only registration after a one-time owner bootstrap.
- The first-owner endpoint requires a high-entropy deployment secret, compares it in constant time, and transactionally locks a migration-created singleton installation record. The status endpoint exposes only whether bootstrap remains required.
- The browser reads the CSRF cookie established by `django-allauth` and sends it as `X-CSRFToken` for login and logout. Session cookies remain HTTP-only; the deployment token and password are never written to browser storage.
- Production mail requires Django's SMTP backend, a valid sender and host, paired credentials, one TLS mode, or an explicit plaintext-SMTP acknowledgement for a trusted private hop. The development Mailpit UI binds only to loopback and must not receive real customer data. General notification mail is queued separately from domain commits, re-authorized item-by-item at send time, rendered only from fixed autoescaped templates, and retains no destination, rendered copy, or raw failure value in its delivery row. Batches are limited to one recipient/surface and 25 items. Time-zone-aware digest and quiet-hour deferral does not consume an SMTP attempt. Delivery administration is MSP-only, metadata-only, MFA-permission gated, and dead-letter retry requires append-only audit evidence enforced by PostgreSQL.
- Invitation management requires the applicable catalog permission and MFA. Raw invitation tokens use maintained high-entropy randomness, are delivered in URL fragments, stored only as digests, rotated on resend, cleared on expiry/revocation, and excluded from API responses and audit metadata.
- Invitation acceptance requires CSRF, consumes a locked invitation exactly once, creates identity and membership atomically, returns one unavailable state for invalid lifecycle conditions, and removes the browser URL fragment before account entry.
- Password recovery returns the same request state for known and unknown addresses, uses expiring single-use Django tokens in scrubbed URL fragments, requires CSRF for mutations, does not auto-login, and invalidates existing password-bound sessions.
- Active browser sessions use maintained allauth records, are listable only by their owner, and require CSRF for revocation. Login and recovery throttles share Valkey across web workers; authentication audits remain append-only and exclude credentials and client/session identifiers.
- TOTP is required for privileged owner actions. TOTP secrets and recovery seeds are envelope-encrypted with the deployment master key; recovery codes are shown only on generation, and sensitive MFA changes require recent password reauthentication. MFA values are excluded from logs, email, and append-only audit metadata.
- OIDC is optional, configuration-driven, and uses allauth's maintained discovery, state, callback, token, issuer, audience, and signature validation. Provider secrets and discovery internals are excluded from public configuration responses; only existing invited identities with a provider-verified matching email can authenticate.
- API bearer tokens are accepted only through the `Authorization` header over the deployment's TLS boundary. Their raw value is shown once, while PostgreSQL retains only a maintained password hash, prefix, exact Workspace, explicit non-MFA permission rows, mandatory bounded expiry, lifecycle, and rate-limited last-use metadata. Issue/rotation is session/CSRF/TOTP/recent-reauthentication protected; service identities are unusable for login and remain read-only. Bearer authentication precedes request-wide RLS, and effective access is the intersection of current account policy, token permission, and exact Workspace. Tokens never appear in URLs, list responses, audits, logs, browser storage, exports, or notifications.
- Central policy authorization with stable permission keys, documented built-in roles, centrally declared MFA requirements, fail-closed organization access modes, and cross-tenant/cross-client negative tests. Views and services do not authorize by role name; frontend visibility is never authoritative.
- Compliance assignment owners are active authenticated tenant users who independently retain `compliance.view` for the exact Workspace; assignment does not grant access. Current applicability/status/due-date projection is separate from append-only exact-revision review evidence, with PostgreSQL scope/actor/retention guards and forced RLS.
- Compliance evidence is reusable only inside one authorized Workspace. Source entities, assignment links, actors, collection windows, and exact control revisions are revalidated in PostgreSQL; retained links and review decisions are append-only. Evidence reuse does not expand its visibility or the viewer's authority.
- Compliance risks are exact-Workspace records with server-derived scores and append-only full-state decisions. Owners and optional control assignments are reauthorized; explicit acceptance records actor/time and cannot be inferred from treatment text. Scoped summaries never aggregate clients.
- Compliance evidence bundles are canonical exact-Workspace manifests signed with the deployment Ed25519 publication key. They retain public verification material and are immutable under Django and PostgreSQL; they are integrity records, not external certification.
- The `0.8.0` compliance-and-monitoring gate composes signed evidence, reminders, approved egress, entered domain truth, bounded DNS/certificate observations, central policy/IDOR, forced RLS, a real exact-client browser journey, exact-prior upgrade, independent restore, and production-target secret-file/image behavior. It grants no client aggregation, remote write, or monitoring-alert recipient authority.
- A maintained certification inventory classifies every tenant-bearing model. Authorization control-plane rows outside RLS use fail-closed scoped managers and database guards that make tenant ownership immutable, require same-tenant relationship edges, and require invitation/administrative actors to be tenant members. The control plane includes immutable Workspace identities resolved before domain RLS binding. Runtime startup verifies that guard inventory. This boundary is certified only for the supported one-MSP-per-installation topology.
- Additive custom roles may target the tenant, one organization, or a maintained access collection, but never bypass assigned-client reachability. MSP-private audience classification and cataloged sensitive-field projection remain hard constraints after role composition. Commercial cost rows are emitted only inside the `costs` member and that member is absent—not null, masked, counted, or summarized—without exact-scope `costs.view`; cost mutation also requires MFA-protected `assets.edit`.
- Recycle-bin reads and restores derive scope from the MSP or exact organization route. Restore requires the central recovery permission, the domain's archive/manage permission, MFA, and CSRF; stale, foreign, sibling, and guessed identifiers do not disclose records.
- Audit evidence is insert-only at both the Django model and PostgreSQL layers. PostgreSQL rejects row updates and deletes; the application exposes no retention bypass. Destructive table/schema administration remains inside the trusted database-owner boundary.
- Schema ownership is isolated to the one-shot migration service. Web, worker, and scheduler processes use a fixed non-owner/non-`BYPASSRLS` PostgreSQL role, validate the expected forced-RLS inventory at startup, and bind tenant/Workspace/organization scope only inside transactions. Missing scope, cross-scope writes, runtime unrestricted mode, and schema changes fail closed.
- Canonical Markdown with no executable raw HTML, MDX, inline styles, or author CSS. Authenticated preview requires `documents.view`, normal CSRF/session protection, and bounded input; server rendering uses a raw-HTML-disabled parser plus explicit `nh3` tag/attribute/scheme allowlists, followed by an explicit DOMPurify allowlist at the single browser HTML sink. A malicious corpus checks authored tags, active unsafe URLs, style/event attributes, and representative MDX payloads.
- Structured document placements keep transclusion outside the Markdown dialect. Live and pinned targets, parent scope, source visibility, ancestor-cycle rejection, MSP-reference dependency retention, and detached replacement scope are enforced in both the service and PostgreSQL layers; resolution and reuse-impact output are bounded. Backlinks expose only documents and client listings the requesting member can already view. Shared edits re-authorize the block owner's scope, while detach requires destination edit authority and never changes the source block.
- Entity mentions store only stable `tekdocs://entity/{uuid}` links. Search and render resolution use exact workspace visibility; authored labels are never trusted for display, and hidden/missing targets collapse to a generic unavailable card. Raw HTML, active URLs, and unsanitized rendered output remain prohibited.
- Managed document attachments store opaque provider keys and stable `tekdocs://attachment/{uuid}` references, never public media URLs. Replaceable storage/scanner adapters place bounded bytes in opaque quarantine, run conservative executable/polyglot, AV-test-marker, active-PDF, image-container, text-control, and ZIP metadata checks, then promote only checksum-verified clean bytes. Rejection, scanner/provider failure, integrity mismatch, or database rollback deletes remnants and creates no downloadable record. Clean status plus provider/engine/time are retained; download, template copy, and STATIC reads recheck size and SHA-256. ZIPs are never extracted and reject traversal, encryption, symlinks, nested archives, excessive members, expansion, and compression ratio. Exact document authorization, forced-download disposition, `nosniff`, private caching, soft removal, PostgreSQL scope guards, and forced RLS remain mandatory. The built-in scanner is not claimed as equivalent to a maintained external malware-signature engine. Markdown import is UTF-8 `.md` only and bounded to 1 MiB; export contains resolved Markdown but never attachment bytes.
- Asset relationships reuse the typed EntityLink policy/RLS boundary and exact active Workspace visibility; client asset search cannot discover sibling records. Bulk asset mutation requires MFA-protected `assets.edit`, accepts at most 100 unique IDs, locks the complete exact-scope set before changing it, runs in one transaction, appends normal lifecycle/audit evidence, and returns one non-disclosing failure for stale or foreign selections. Bulk disposal is prohibited; recoverable archive rejects software installations with active license coverage or seats.
- STATIC publication runs only in the source document's owning workspace and freezes exact authorized block revisions, entity projections, and source-owned attachment bytes into a versioned canonical manifest. Missing or foreign dependencies fail atomically. Canonical Markdown, sanitized HTML, and manifest bytes use an unambiguous length-delimited snapshot format whose SHA-256 digest is signed with Ed25519. The private key is deployment-supplied and never returned or stored in PostgreSQL; retained publications contain only public verification material. New publications retain a deterministic PDF and independent attachment copies under opaque names; reads recheck signed sizes and SHA-256 checksums. Mandatory reason, intended audience, retention, and append-only correction metadata are signed. Django/PostgreSQL reject publication and artifact mutation, forced RLS preserves client isolation, deferred guards require a complete signed artifact set, and failed operations remove partially written bytes.
- Publication audience labels are not access grants. Distribution decisions live in a separate append-only ledger: client-visible material remains unavailable until a different MFA-reauthenticated user with scoped `documents.approve` authority approves it. Withdrawal removes availability without erasing evidence. Approval/withdrawal routes use central policy and non-disclosing lookup; PostgreSQL independently checks Workspace scope, event order, actor separation, one approved correction successor, immutability, and forced RLS under advisory locks. Existing publications are compatibility-backfilled as historically approved, so operators must review legacy client-facing content before enabling a future portal.
- Client accounts carry an immutable exact-client organization binding and an explicit portal session surface. The central MSP permission boundary rejects client roles wholesale; portal endpoints derive organization scope only from membership and reject MSP sessions. PostgreSQL repeats role/scope, tenant, active-client, and retargeting checks. A client browser renders no MSP navigation or workspace selector.
- Client portal documentation is a fail-closed projection of active approved client-visible STATIC publications. Approval and portal reads require embedded entity references to be client-visible in the exact organization; unsafe historical projections and MSP listing references are not exposed.
- Notification-producing domain changes use a transactional outbox with exact tenant/organization ownership, fixed topic payload schemas, immutable payloads, forced RLS, bounded retry, value-free error codes, and append-only idempotent consumer receipts. Raw exception messages, email addresses, document text, reasons, and secret material are prohibited from event payloads.
- Inbox rows retain only an immutable recipient/event/surface edge plus mutable read time. MSP and portal APIs re-authorize the source and exact organization before constructing fixed display copy or typed navigation; withdrawn client content receives no title or link, and stale authority omits the row. Responses are private/no-store and read changes require CSRF.
- Credential-reference records contain provider pointers only. Separate view, manage, and open permissions are scope-aware; list/search responses omit provider links, and the audited handoff revalidates the target before redirecting. Share links, arbitrary URLs, secret-shaped input fields, provider retrieval APIs, value proxying, and customer-secret storage are prohibited.
- Supplier catalogs exist only in vendor/manufacturer workspaces and use stable product/model identities plus immutable schema and model revisions. Specification schemas are closed, size/property bounded, and restricted to a maintained scalar/string-array vocabulary without remote references, authored regular expressions, compound evaluators, or executable extensions. Values are validated server-side; updates require the exact base revision. Central `assets.view`/`assets.edit` policy, exact workspace scope, database edge guards, append-only triggers, and forced RLS protect the catalog history.
- MSP/client asset creation accepts only an addressable active supplier model and derives every ownership/provenance field server-side. MSP ownership is the installation's one explicit MSP Workspace; `organization IS NULL` is only its guarded scope projection and never means all client organizations. The asset retains exact supplier/product/model/revision/specification identifiers, validated values, and a checksum; applicable documentation retains exact verified `client_visible` STATIC publications and digests in append-only rows. Database triggers reject Workspace/scope retargeting and provenance mutation. MSP/client-mode RLS adds read-only access to supplier catalog rows and only those STATIC publication/document/artifact rows explicitly associated with a product; unrelated supplier documents, client operational records in MSP mode, and every cross-scope write remain unavailable. Vendors is a grouped projection of retained supplier identity, never a label match or implicit relationship.
- Hardware lifecycle uses a hardware-only client-scoped current-state profile and an append-only typed event ledger. Serial/tag normalization, acquisition and warranty dates, exact-client active person/site/location assignments, terminal disposal, profile/event edges, event immutability, and forced RLS are enforced in both application services and PostgreSQL. Mutation audits and lifecycle events omit acquisition/warranty references, disposal reasons, and other free text.
- Software licensing uses a software-only client installation profile plus addressable product-bound entitlements. Exact-client/product installation links, seat limits, person/installation targets, renewal constraints, append-only value-minimized history, PostgreSQL guards, and forced RLS prevent cross-client assignment and history rewriting. License references are excluded from audit metadata; license keys and credential values are not accepted.
- Redacted structured logs, append-only audit records, scoped API/service credentials, and webhook replay protection.
- Organization webhooks use one-time envelope-encrypted signing keys, canonical HMAC-SHA256 signatures, delivery-ID/timestamp replay protection, append-only receipts, bounded retry/dead-letter state, metadata-only inspection, and a pinned public-HTTPS transport that disables redirects. Inbound payload semantics are limited to a value-free ping until a reviewed provider contract exists.
- Customer credential values are not stored or retrieved by TekDocs. Credential records are strictly validated external references; 1Password unlock, authorization, reveal, and value audit remain in 1Password.
- Runtime deployment secrets resolve through one mutually exclusive direct-or-`*_FILE` reader. Production Compose mounts bounded, validated files only into the database/migration/runtime/auth service that needs them; the production rehearsal rejects ambiguity and checks container environments, image history, and logs for value leakage. An unclaimed installation is unready without its separately mounted bootstrap token, while a claimed installation permits permanent token removal. Direct environment compatibility remains development-only policy work to remove at `0.8.7`.
- Supported recovery encrypts PostgreSQL, managed media, and an allowlisted deployment-key archive as authenticated streams with a separately custodied 256-bit key. Restore authenticates every artifact before exact-project destructive work, rejects unexpected members and existing secret output, and restores non-owner runtime grants. The recovery key must never share custody with the application, backup set, or deployment-secret directory.
- SSRF-resistant outbound integration and monitoring requests.
- Dependency, license, secret, source, container, and browser security gates.
- Reviewed Python build/production/development hash locks, digest-pinned external images and local scanners, commit-SHA-pinned Actions, local workflow linting, and controlled Dependabot updates.
- A blocking PostgreSQL stabilization gate that combines bounded policy-aware query paths, representative migration reversal/reapplication, the complete authenticated-route and IDOR matrix, scoped custom-role composition, recovery, audit immutability, and raw non-owner RLS checks. Performance work may not cache or bypass authorization scope.
- A dedicated PostgreSQL documentation-certification gate that composes document/publication behavior, hostile rendering, the complete authenticated-route and IDOR matrix, raw non-owner RLS checks, and the authorization-aware 2,500-revision reference fixture. It supplements rather than replaces browser, security, production-image, upgrade, and database/media recovery evidence.
- A dedicated PostgreSQL inventory-certification gate that composes supplier catalogs, retained asset provenance, hardware/software lifecycle, entitlements, contracts/cost projection, credential references, hostile attachments, typed relationships, recovery, the complete authenticated-route and IDOR matrix, raw non-owner RLS checks, migrations, concurrency, and the authorization-aware inventory reference fixture. It supplements rather than replaces browser, security, production-image, upgrade, and database/media recovery evidence.
- A dedicated PostgreSQL controlled-client-access certification gate that composes client identity/invitations, publication decisions, portal projection, transactional outbox, inbox, SMTP delivery, digest/quiet-time preferences, metadata-only administration, signed histories, the complete authenticated-route and IDOR matrix, raw non-owner RLS checks, migrations, scale, and frontend accessibility behavior. It supplements rather than replaces the real publisher-to-approver-to-client browser journey, production-image, exact-prior upgrade, and database/media recovery evidence.
- Portal document, inbox, and delivery-history cursors are signed, 30-day, seek-only values bound to the exact account and access surface; a delivery cursor also binds its state filter. They contain ordering keys rather than data or authority. Tampering, cross-user replay, surface/filter replay, and expiry fail closed. Page and authorization-scan bounds apply before serialization, while every notification remains subject to current source, audience, client-membership, and permission checks.
- Keyboard and axe regression coverage for implemented MSP/client workflows, unavailable and capability-denied states, direct routes, history, mobile context changes, and stale workspace responses across the release browser matrix.

Production startup must fail for missing or placeholder secrets, wildcard hosts/origins, insecure cookies, inadequate HSTS, mismatched public/CSRF origins, incomplete OIDC settings, debug mode, or an unsupported database configuration. The development Compose stack's HTTP origin requires the explicit localhost-only insecure-public-URL acknowledgement.

See `docs/THREAT_MODEL.md` for the initial abuse analysis. Security reports are handled according to root `SECURITY.md` once the public repository is published.

## Inventory and external-reference certification

Operational collection pagination is never an authorization mechanism. TekDocs resolves the exact MSP or organization Workspace and central permission before applying a bounded page; count and continuation metadata therefore describe only that authorized Workspace. Cost-denied contract responses omit the complete protected member, and list/search responses never contain 1Password Private Links. Provider handoff remains a separately authorized redirect with value-free audit metadata, and the interface tells operators to replace a stale pointer rather than implying that TekDocs validated the provider item.

The `0.4.0` inventory certification runs on PostgreSQL and combines supplier catalogs, competing seat allocations, immutable provenance recovery, CSV/bulk rollback, archived-pointer denial, hostile attachment handling, typed relationships, cross-Workspace IDOR, forced RLS, bounded reference performance, migration state, and clean `0.3.12` upgrade/restore rehearsals. This does not turn the structural attachment scanner into an external signature engine or make the host/container administrator untrusted.

Network placement added in `0.4.1` remains inside the same exact-Workspace and central-policy boundary. Site, location, rack, and optional hardware-asset edges are revalidated in PostgreSQL; rack occupancy uses both service row locks and a transaction advisory lock before overlap checks. MSP network routes select only MSP-owned rows and are not cross-client reports. Recovery, bulk transfer, and final network scale certification remain assigned to later network milestones.

Network addressing added in `0.4.2` applies the same boundary to VRFs, VLANs, and subnets. The default routing table and each VRF are separate overlap namespaces. CIDR canonical form, derived family, VLAN bounds, same-Workspace ownership edges, and overlap are enforced in both the service and PostgreSQL; advisory locks prevent concurrent check-then-insert races. A VLAN is not treated as a routing-isolation boundary.

Endpoint addressing in `0.4.3` extends that boundary to interfaces, IP hosts, and MAC addresses. The server resolves every device, subnet, and interface edge inside the route's exact Workspace; forced RLS and database triggers repeat those checks. Canonical IP/MAC forms are required, IPv4 reserved-host rules are enforced, and shared PostgreSQL advisory locks make IP conflict decisions atomic with subnet edits. Duplicate IPs fail only inside one routing namespace; duplicate MACs fail across the entire Workspace. Validation and audit payloads do not disclose sibling topology.

Wireless and DNS inventory in `0.4.5` remains behind the same exact-Workspace central network permissions. Wireless input contains no credential field and strict serializers reject password-shaped additions; access material belongs in external credential references. DNS owners and values are bounded and type-aware, A/AAAA links must match an authorized IP record, CNAME coexistence is serialized, and PostgreSQL independently enforces scope/canonical/relationship rules under forced RLS. These records are maintained inventory only: no DNS lookup, serving, outbound validation, wireless control, or customer-secret custody occurs.

Circuit inventory delivered in chronological build `0.4.6` uses exact-Workspace `networks.view` and MFA-backed `networks.edit` throughout. Providers must be eligible same-tenant organizations; optional contracts must match both provider and Workspace, and linked contracts cannot be archived. Handoff site/location/device/interface edges are independently revalidated by PostgreSQL under forced RLS. Contract lifecycle fields are omitted unless the caller has `assets.view`; costs and other financial terms are never projected by network APIs. Password-shaped and unknown fields fail closed, audit metadata contains no service values, and lifecycle reminders are calculated dates rather than outbound jobs.

NetBox identity mapping began as an offline preview in `0.4.7`. The `0.6.4`–`0.6.7` runtime resolves one exact Workspace and central integration permission before using a read-only connection. API tokens are envelope-encrypted, never returned, and decrypted only inside a worker request. Public-HTTPS address pinning, TLS hostname verification, no redirects, same-origin bounded pagination, durable idempotent jobs, and value-minimized observations/logs/conflicts form the provider boundary. Raw provider JSON is hashed then discarded. Reconciliation never writes back or mutates TekDocs domain data; accepting remote updates only an existing mapping fingerprint. `0.6.9` adds blocking adversarial egress, transactional retry, lease-recovery, scale, exact-prior upgrade, independent restore, and production-image evidence; their composed certification owner is `0.7.0`.

`0.7.0` certifies that API sessions/tokens, signed webhooks, provider workers, reconciliation, and sanitized exports preserve the same exact-Workspace policy and forced-RLS boundary. This claim remains limited to read-only providers and local sanitized export artifacts; it grants neither third-party write-back nor remote Git credentials.

`0.7.7` centralizes public-HTTPS destination validation for outbound calls. Every DNS answer must be globally routable, the reviewed address is pinned for the connection while TLS verifies the authored hostname/SNI, redirects remain disabled, and callers retain explicit time/body/content/origin limits. DNS and a remote service remain untrusted inputs; this boundary must be used by later domain and certificate collectors.

Compliance catalogs introduced in `0.7.1` separate stable framework/control identity from immutable content and ordered catalog snapshots. Central compliance permissions, exact-Workspace queries, strict bounded inputs, SHA-256 digests, PostgreSQL relationship/retention triggers, forced RLS, and sibling IDOR tests prevent ordinary application/runtime writes from retargeting or rewriting historical baselines. Digests detect change but are not signatures, and a host/database administrator remains trusted. TekDocs does not claim that catalog presence proves applicability, implementation, evidence, review, or certification.

Compliance evidence introduced in `0.7.3` remains a scoped documentation object rather than proof by itself. One evidence identity can be reused across multiple controls in the same Workspace, while retained links pin each exact control revision and append-only reviews preserve decisions over time. Central policy, non-disclosing APIs, database edge/actor/window guards, forced RLS, and negative tests prevent sibling reuse or history rewriting. Signed evidence bundles and certification claims remain outside this boundary.

The `0.7.4` risk register applies the same boundary to operational risk decisions. Likelihood and impact are bounded inputs while score/band are derived, treatment and acceptance are explicit, owners are currently authorized users, and deadlines/reporting are calculated only after exact-Workspace authorization. Each decision retains a full snapshot and exact control revision when related. Risk acceptance is an accountable decision, not proof of remediation or certification.

Shared reminder schedules use dedicated central permissions and exact-Workspace source validation. Calendar export is an authenticated, bounded, private/no-store download; TekDocs does not issue persistent public calendar tokens in `0.7.6`. Schedule visibility never grants access to the related compliance or inventory object.

Registered-domain inventory is exact-Workspace data under dedicated domain permissions and forced RLS. Domain identity normalizes to IDNA ASCII; entered registrar, dates, renewal mode, owner, status, and notes are not treated as remotely verified truth. MSP routes never aggregate client registrations.

Hostname hierarchy cannot leave its exact registered-domain Workspace, and parent edges must be DNS ancestors. DNS records are bounded append-only observations with explicit source/time/provenance and content digests; they do not overwrite entered ownership or renewal claims.

Domain expiration schedules reuse the dedicated deadline permission and exact-source boundary. Current/stale/conflict reviews are retained events, and observed dates never silently replace entered values. Notification sending is excluded from request transactions and awaits a bounded reminder dispatcher.

Domain monitoring is worker-only and exact-Workspace scoped. RDAP and DNS-over-HTTPS destinations pass the shared public-HTTPS, every-answer, address-pinning, hostname-verification, no-redirect, timeout, content-type, and response-size controls. Raw responses and exception text are not retained. Automated review events, normalized DNS answers, run evidence, and alerts are source-attributed and protected by database guards plus forced RLS; entered registration values remain unchanged.

Certificate monitoring is also worker-only and exact-Workspace scoped, but uses a narrower direct-TLS boundary rather than arbitrary URLs. Operators choose an authored domain/hostname and one of four fixed protocol/port pairs. Every DNS answer must be globally routable, the connection uses a reviewed pinned address with the authored name as SNI, and TLS 1.2 or later is required. TekDocs separately records hostname and CA trust results, retains only bounded certificate digests/metadata, and discards certificate bodies and exception values. Custom ports, STARTTLS, private destinations, redirects, and proxying are not supported.

Network search/export in `0.4.8` remains an exact-Workspace read boundary. Search returns only stable identity, label, type, and owning section after central `networks.view`; it does not echo the matched field. The versioned CSV is an explicit streamed projection, not model serialization: costs, contract data, asset-only fields, credential references, provider payloads, and NetBox fingerprints are excluded, every cell is spreadsheet-escaped, and private/no-store headers prevent shared-cache retention. MSP routes remain non-aggregating.

The `0.4.9` lightweight boundary requires every newly created network-device record to extend an active exact-Workspace hardware asset. Database guards independently reject missing, reused, non-hardware, archived, or cross-Workspace edges and prevent application-created legacy markers. Direct IP/MAC asset assignment is exact-scope and the asset identifier/name is projected only with independent `assets.view`; `networks.view` alone is not an asset oracle. Pre-existing Interface/VRF-era rows are retained, explicitly labeled, and upgraded only through stable foreign-key chains—never mutable display-name matching.

`0.5.0` certifies this boundary through the composed network gate, direct/concurrent PostgreSQL negatives, 100-client scale fixture, exact prior-version upgrade, independent restore, production-shaped browser path, security scans, and production-image checks. Certification is local evidence, not a claim of live network truth, live NetBox trust, external assessment, or published artifact provenance.
