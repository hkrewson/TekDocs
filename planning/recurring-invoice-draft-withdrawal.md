# Retained recurring-draft withdrawal — 0.8.46 checkpoint

Issue #76 pre-1.0 implementation checkpoint. Version remains `0.8.46`. This
slice adds the retained data, service, API, and operator workflow for withdrawing
an unissued recurring draft. The invoice, generated line, approved terms, and
permanent period claim remain intact.

## Delivered boundary

- `RecurringInvoiceWithdrawal` is an append-only, one-per-period disposition
  with the exact organization scope, first reason, actor, and time.
- Withdrawal accepts only an unissued draft generated by a recurring-period
  claim. It requires invoice edit permission, MFA, recent reauthentication, and
  a non-empty bounded reason.
- Retrying withdrawal returns the first retained disposition. It does not
  replace the reason or create another audit event.
- A withdrawn recurring draft cannot be edited, issued, receive another line,
  or have a line changed or deleted. The existing rule also continues to block
  deletion of every generated recurring invoice and line.
- Invoice detail and collection responses include the recurring service period
  and derived `active` or `withdrawn` disposition. Withdrawn responses include
  the retained reason and time so interfaces can present them as history rather
  than actionable drafts.
- The invoice record replaces deletion with a focused **Withdraw draft** action
  for active recurring drafts. Confirmation names the consequence and requires
  a reason; expired recent authentication opens the existing password check and
  safely resumes the same idempotent withdrawal.
- A withdrawn record is read-only, shows its service period, withdrawal date,
  and retained reason, and offers no issue, edit, line-add, or line-change
  controls.
- Ordinary invoice collection requests exclude withdrawals. The explicit
  **Withdrawn** status filter provides retained history access, including stable
  direct record URLs.
- The audit event contains the invoice identity and action only; the operator's
  reason is retained on the protected disposition and is not copied into audit
  metadata.

## Database and recovery contract

PostgreSQL validates period, invoice, line, tenant, organization, actor, draft
state, and reason on insertion. Dedicated triggers reject disposition updates
and deletes and freeze the withdrawn invoice and its lines beneath the service
layer. The new table has forced organization-scoped row-level security and is
included in the central RLS contract.

Migration `0153_recurring_draft_withdrawal` is additive. Its retention function
is self-contained so the earlier recurring-guard rollback rehearsal can remove
and restore its own functions without affecting newer retained records.

## API contract

`POST /api/v1/workspaces/organizations/{organization}/invoices/{invoice}/withdraw-recurring-draft`
accepts `{ "reason": "..." }` and returns the invoice with its recurring
disposition. Existing invoice and recurring-generation routes remain compatible.
OpenAPI and generated browser types include the additive response data and
withdrawal route.
