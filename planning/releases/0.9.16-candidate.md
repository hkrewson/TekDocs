# 0.9.16 candidate: retained Git-backed publications

Prepared October 27, 2026 on main, following `v0.9.15`
(`6a06b2acdbe042d93aa993e3f8f649ce5ca5aab0`). The maintainer authorized the real
browser acceptance journey, release preparation and direct main commit/push after
validation. Production deployment and Wiki publication remain separate actions.

## Release notes

- Migrate supported ordinary documents with verified internal, permanent signed
  publication history. Import plans bind that history; promotion, rollback and
  re-promotion preserve original signatures, manifests and retained PDFs.
- Publish signed v5 snapshots from exact accepted Git content. Corrections may
  supersede supported legacy or Git snapshots; withdrawal and decisions remain
  append-only. Runtime-role predecessor lookup preserves immutable-row access.
- Connect promoted documents to publishing, corrections, withdrawal, retained
  history and PDF downloads. Readiness uses current pinned Git content and fails
  closed without a historical database fallback.
- Keep correction controls available for authorized publication links whose
  source document is outside the current page or filter. The focused source is
  retained separately and scoped to its Workspace.
- Add a required browser-to-PostgreSQL acceptance gate using real migration
  services, managed Git, actual HTTP, restricted database connections and real
  retained PDF downloads. Generated sessions remain private temporary inputs;
  retained artifacts contain only sanitized result summaries.
- Keep machine-specific agent instructions ignored and outside public source.

This is a bounded internal/permanent publication checkpoint. Templates,
managed-file documents, unresolved keys/references and broader client delivery
remain outside this migration/publication shape. Existing native repository
publication paths are distinct. Document copy and promotion remain explicit operator actions; upgrading applies
the normal Django schema migrations.

## Acceptance and evidence

The real journey creates a legacy signed publication, changes the draft, copies
and promotes the document through production migration services, then uses the
interface to publish, edit Git, correct both legacy and Git snapshots, withdraw,
read decisions and download PDFs. It exercises a publication excluded by the
current search filter, a denied read-only publication attempt with its draft
preserved, read-only retained PDF access and anonymous denial. The server then
verifies original bytes/signature, all retained custody, rollback and re-promotion.
The browser's authenticated sessions are generated by the test client; interactive
bootstrap/login/MFA remains covered by the separate existing live-workspace gate.

The gate reuses the standard project's database, migrate and frontend services;
its generated PostgreSQL test database is separate from retained development
records. Official Django test settings use an in-memory cache because the local
retained Valkey service has an unrelated restart fault. Hosted production-image,
DAST, recovery and upgrade gates remain required for the exact release commit.
The private handoff directory permits only its host owner and fixture service
group; generated session input remains service-owned `0600`. A native Linux UID
replay verifies this boundary and the value-free result/status exchange.

The [source review](0.9.16-source-review.md) keeps Standards and Spec findings
separate. Earlier CI at `65302e4` and `aa2cd43` is supporting source evidence,
not relabeled as this version's release evidence.

## Hosted preparation follow-up

The first 0.9.16 push, `586be15`, reached hosted validation in
[Build 40635810767](https://github.com/hkrewson/TekDocs/actions/runs/40635810767).
Its existing real workspace journey passed, but the new publication phase failed
before browser startup: migration 0019 requires the runtime database role. The
harness had skipped normal role provisioning; the retained local database masked
that prerequisite. A Docker replay of the unchanged migration guard against a
deliberately absent role reproduced the exact exception without removing the
retained role. The follow-up invokes the existing provisioning command against
the configured base database before pytest creates its separate test database.
Browser assertions and migration code remain unchanged. The complete Docker
journey passes after provisioning, including server custody/authority checks and
artifact hygiene; nine focused tooling checks and shell syntax pass. A fresh
complete hosted run must confirm the correction before release delivery.
