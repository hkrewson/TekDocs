# 0.9.7 progress: exact Git publication-source evidence

Updated: 2026-10-08. Application version remains `0.9.6`. This is the first
internal foundation for [issue #106](https://github.com/hkrewson/TekDocs/issues/106),
not a `0.9.7` release or an authority handoff.

## Bounded result

`freeze_git_document_dependencies` produces a deterministic, value-free proof
of one repository document's accepted commit, root Markdown blob, and ordered
audience-visible live or pinned fragment blobs. It records path, commit, blob
ID, exact-byte SHA-256, and composition identity. It re-reads Git content,
recomputes the bounded composition, checks the current index, and fails closed
on index lag, projection drift, or missing pinned source objects. There is no
new route, database schema, or stored publication format in this step.

The second internal foundation provides `pinned_git_document_dependencies`, a
transactional source-proof context for a future repository publisher. It holds
the managed Git lock before the repository database row lock, recomputes the
proof under both locks, and rechecks accepted/indexed identities and Git head
before commit. A concurrent authoring commit waits until the context ends;
an exception or state change rolls back the attempted retention. It also works
inside the authenticated request's outer transaction: the repository row lock
persists until that transaction commits.

The third internal foundation retains one composed Markdown snapshot and the
exact Git dependency proof in a separate signed, append-only, exact-Workspace
record. It uses the deployment publication signing key and verifies the
retained text, manifest, source identity and trusted key without consulting
the live repository. PostgreSQL insertion guards, forced RLS, and update/delete
triggers protect the record below the service layer. Publisher permission and
MFA are required. This is evidence for a future repository STATIC path, not
a routed, approved, downloadable or portal-visible publication.

The fourth internal foundation adds a deterministic publication-readiness gate
inside that pinned retention. It signs only nonempty, structurally complete
compositions whose dynamically rendered dependencies are already frozen.
Until repository packaging exists for them, attachment, key, entity-card,
image, unknown TekDocs-link, and Mermaid dependencies block retention with
value-free finding codes. Literal code examples are ignored. The selected
audience's composed Markdown and a versioned preflight summary are signed;
older signed evidence without that optional summary remains verifiable but
does not attest publication readiness. This does not change legacy publication
behavior or expose a new route.

The fifth internal foundation retains managed attachments referenced by a
copied repository document. A link is eligible only when the matching active
legacy document owns a clean attachment in the same Workspace. Retention
rechecks its exact bytes and copies them into a separate private artifact;
the signed evidence manifest binds each artifact's identity, source identity,
size, checksum and media type. Verification reads the retained copy, not the
live source. Missing, foreign, corrupt, primary-file or over-limit references
fail closed. The additive artifact table has forced exact-Workspace RLS and
append-only database guards. This does not publish or distribute files, nor
support repository-native attachment ownership yet.

The sixth internal foundation freezes narrative entity cards into signed
repository evidence. The existing permission-filtered relationship resolver
supplies a locked display snapshot; exact-Workspace ownership and
client-audience visibility are checked before signing. Verification compares
the retained cards with links in retained Markdown without consulting live
entities, so later renames do not rewrite evidence. Missing, foreign and
private client-audience targets are refused. This stores no operational asset
or organization state in Git and adds no publication route.

The seventh internal foundation freezes portable, field-only document keys
into the same protected signed evidence. The repository root's portable
`key_bindings` must exactly match the active legacy document's bindings in
that Workspace. Existing key resolution applies the selected audience's
record and sensitive-field permissions under locks; unavailable, changed,
content-expanding, or client-withheld keys fail closed. The authored Git
Markdown retains key expressions and target identities, never resolved values.
The protected evidence manifest retains a frozen rendered projection and
provenance records, which verification reconstructs from signed data without
reading mutable asset fields. This is still internal evidence, not a routed
publication or a repository-native key-binding authoring path.

The eighth internal foundation makes new signed evidence self-check its
dependency closure. The manifest retains the selected topic type, and offline
verification reruns the deterministic preflight against the retained Markdown
and frozen attachment, entity-card, and key identities. Attachment descriptors
must cover exactly the references in the retained text. This catches an
internally inconsistent but otherwise correctly signed manifest without
reading Git, mutable assets, or source files. Older evidence without a topic
type remains verifiable under its original checks but does not claim this new
closure attestation. Source pinning also compares indexed topic and frontmatter
fields with the accepted Git root, so a stale projection cannot weaken the
preflight or binding check. No publication or distribution route is added.

The ninth internal foundation retains sanitized HTML rendered solely from the
signed evidence inputs: authored composition, frozen field-key values,
entity-card labels and attachment descriptors. Attachment filenames are signed
for the rendered card, but no download URL or distribution permission is
created. Verification recomputes the HTML without live Git, assets or source
attachments and rejects even a correctly re-signed inconsistent projection.
The output has an explicit size limit. Earlier evidence without this optional
rendered snapshot remains verifiable without claiming an HTML attestation;
this is not yet the routed or downloadable STATIC artifact.

The tenth internal foundation retains a private PDF projection of the same
accepted composition. Its title is checked against the accepted Git source;
frozen field-key values, when present, are used for rendering. The signed
manifest binds the PDF format, exact bytes, size and checksum, and offline
verification checks the signed descriptor against the retained file.
The additive file field is constrained to an evidence-specific storage path;
older evidence without a PDF remains valid without claiming a PDF attestation.
The PDF renderer preserves the legacy textual Markdown/diagram fallback and
does not yet supply repository-specific distribution or attachment download
links. It is not an approved, routed or downloadable STATIC artifact.

The eleventh internal foundation separates retained artifact integrity from
current-renderer reproducibility. Signed HTML is checked against its own
size and checksum, and the private PDF against its signed size, checksum and
exact bytes. Verification no longer makes historical validity depend on the
installed Markdown/PDF renderer; the legacy STATIC verifier uses the same
signed-byte principle. An opt-in reproducibility diagnostic compares each
retained snapshot with the current renderer, without changing validity or
making the ordinary verifier execute rendering code.
New source proofs also bind the root title independently of the PDF manifest;
earlier signed evidence without that optional title proof remains verifiable.
Renderer drift must be reviewed before a new publication is approved, but it
cannot erase the integrity of an already retained artifact.

## Validation and remaining work

The synthetic PostgreSQL/Docker composition suite covers nested pins, live
sources, audience filtering, exact SHA-1 Git blob identity, deterministic
repeat, projection tampering, accepted-head lag and missing pinned objects.
The broader `make test-content-composition` gate passed locally against the
signed-evidence foundation and its predecessors. Repository-wide `make check`
also passed for this slice, including frontend tests/build, backend lint and
typing, migration drift, and OpenAPI. The lock test uses separate PostgreSQL
connections to verify that a concurrent writer cannot advance the head while
the retention context is open. A further race test proves the database row
remains pinned until an authenticated request's outer transaction commits.
Rollback and stale-index rejection are covered. Evidence tests cover publisher
MFA denial and allow, exact-client and foreign-tenant runtime isolation,
signature and retained-byte tampering, database-level insert/update/delete
guards, verification after the live head advances, and an `0167`→migration-head
upgrade with forced RLS restored in `finally`.
The readiness tests exercise each unsupported dependency, literal code,
topic-section blockers, signed preflight identity, and refusal to insert
evidence when a required artifact is not frozen. Attachment tests cover exact
copy and checksum, verification after the source disappears, retained-copy
loss, missing ownership, append-only guards, and an `0168`→head upgrade.
Entity-card tests cover retained-name stability, manifest tampering, private
client-audience denial and sibling-client denial. This slice has no schema or
public API change.
Field-key tests cover frozen value stability after live rename, protected
snapshot tampering, exact portable binding parity, client withholding, and the
preflight default that blocks unfrozen keys. No schema or public API changes.
Dependency-closure tests cover a re-signed preflight/topic mismatch, unsupported
topic metadata, a re-signed attachment identity mismatch, and compatibility
with earlier evidence that lacks the optional preflight summary. Source tests
also reject tampered indexed topic and frontmatter metadata.
Rendered-snapshot tests cover signed HTML agreement, frozen key and entity
labels after live changes, inert attachment cards, re-signed projection
tampering and backward compatibility.
PDF tests cover exact retained-byte verification, missing-file refusal,
re-signed title drift, source-title projection drift, older evidence without
a PDF, and an `0169`→head schema upgrade with forced RLS retained.
Renderer-compatibility tests replace the current renderers after retention:
signed artifact integrity stays valid, reproducibility reports drift, and a
changed signed checksum still fails closed. No schema or public API changed.

Repository recovery now checks every database-tracked Git commit in the
installed repository during final verification, in addition to matching the
archive, Git object format and accepted head. Backup creation refuses a
mixed-format verified-commit inventory instead of silently omitting those
rows. Focused tests cover a missing retained commit and mixed-format refusal.
The repository-inclusive encrypted backup and network-isolated restore path
already exists; this hardens its final check, not a new backup format or a
completed production restore rehearsal.

The next bounded slice exposes a staff-only, MFA-gated API to retain repository
publication evidence and review scoped summary metadata. MSP and organization
routes enforce exact Workspace ownership; client portal users cannot access
them. List results are paginated, and neither list nor detail exposes retained
Markdown, resolved keys, attachment bytes, PDF bytes or the signed manifest.
The detail response verifies retained evidence offline. This is a candidate
review entry point, not approval or distribution of a STATIC publication.

An approver with document-view permission and MFA can now read the exact
retained canonical Markdown through a separate, exact-Workspace review route.
The route verifies the signed evidence and retained artifacts before returning
content; a missing or altered artifact fails closed. The response does not
include rendered key values, the signed manifest, PDF or attachment bytes.
Tests cover the retained text after the live Git head advances, role denial,
client portal and sibling-organization denial, and corrupt-artifact refusal.
This is review material only: no approval decision, client distribution or
authority handoff is implied.

A separate internal decision route records one final, append-only review
outcome for exact client-visible evidence: `accepted_for_packaging` or
`rejected`, with a required reason and reviewer identity. Acceptance requires
an MFA-gated approver with document-view permission who did not sign the
snapshot; the evidence and retained artifacts must verify at decision time.
The decision is exact-Workspace isolated and cannot be changed or repeated.
It is not a legacy STATIC approval, does not authorize distribution, and
creates no client listing, portal access, notification, export or download.
Final packaging and publication must independently enforce their own controls.

An MFA-gated staff reviewer can now download the exact retained PDF for the
same scoped evidence. The route verifies the signed evidence and all retained
artifacts, then separately checks the bytes it returns against the signed PDF
descriptor. Missing, altered or oversized bytes fail closed. The response is
non-cacheable and forces download; client users and sibling Workspaces cannot
use it. This is private review of a candidate, not a client PDF publication.

The same staff-only review boundary now allows downloading a retained attachment
by its evidence artifact ID. It checks the signed evidence, then independently
checks the exact returned bytes against the signed descriptor, with a bounded
read and a forced generic binary download. Source attachment changes do not
alter the retained copy. Missing or changed bytes, client users, and other
Workspaces fail closed. The verified staff review includes attachment IDs and
display metadata so reviewers can request the retained files. This does not
create a client file route or authorize distribution.

An MFA-gated reviewer can also download the exact retained sanitized HTML
projection. The response requires signed-evidence and HTML-integrity checks,
is non-cacheable, forces download, and carries a restrictive sandbox policy.
It does not rerender current source or grant a client page route. Source changes,
missing retained artifacts, client users, and other Workspaces fail closed.

The existing STATIC publisher remains database-authored. Integration of this
evidence with final publication artifacts and distribution, repository-native
attachment ownership and client delivery, editable and
sanitized exports, templates/monitored sources, client listing/portal parity,
production recovery fault rehearsals
remain open in `0.9.7`. No
production cutover, deployment, or hosted CI result is claimed here.

The integrations API now also accepts `include_repository: true` when creating
a sanitized Git export. It packages every Markdown file in the exact accepted,
fully indexed Workspace repository snapshot, with the accepted commit and
sanitized-file hashes in the manifest. Known credential-reference identifiers,
typed credential links, key bindings, 1Password links and live managed-attachment
links are omitted; malformed, unavailable, lagging or over-limit snapshots fail
closed. The existing document/STATIC selection remains available. The ZIP has
no Git history or attachment bytes and is neither an editable export nor a
complete backup. Authored prose can still contain other secrets and must be
reviewed before sharing. The browser now offers repository-only or mixed
sanitized Git ZIP selection, keeps choices after a failed request, and
identifies the accepted Git version and Markdown count in retained bundles.
Other export formats and full parity remain open; no production deployment is
claimed.

Staff can now download the exact loaded repository Markdown file from the
Repository content editor. It includes portable frontmatter and preserves the
loaded accepted Git revision, even when the browser has unsaved edits. The
revision and scope are explicit in the interface. It is an editable source file
for one document or fragment, not a dependency-complete export, Git-history
transfer or backup. The broader file/export and recovery gates remain open.

A second editable-source slice adds a staff-only current-Workspace Markdown
snapshot ZIP. It retains exact source bytes from one accepted-and-indexed Git
commit, plus reachable historical include, template-source, and copy-provenance
Markdown, with a deterministic commit/path/hash/role manifest; lagging, unavailable and
over-limit repositories fail closed. The browser offers the download with a
retryable failure state and an explicit unsanitized/not-a-backup warning.
Successful downloads leave a value-free audit event with commit and file count.
Nested dependencies inside a historical file resolve in that file's commit.
Unrelated historical files are excluded. Attachment bytes, database records
and Git history remain excluded. Complete editable dependency bundles and recovery acceptance
are still open; this does not change publication or write authority.

An offline verification command now checks the source ZIP's v3 manifest,
bounded and safe entries, exact Markdown IDs/kinds and SHA-256 digests. Missing,
altered, duplicate and unlisted files fail closed. The result proves only ZIP
internal consistency, not authenticity against Git, importability, attachment
parity, database recovery, or backup completeness.

An accepted client-visible review can now produce one immutable, exact-Workspace
repository package candidate. Creation re-verifies the signed source, retained
HTML, PDF and attachments without consulting the live Git head. Its manifest
binds the evidence digest, accepted decision, source commit, and artifact hashes;
a separate digest and append-only database guard protect the handoff record.
Only MFA-gated staff with document-publish and view permissions can create or
inspect it. Client users and sibling Workspaces cannot reach it. This is an
internal handoff record, not a STATIC publication or approval to distribute;
the existing database-authored publisher and all client routes remain unchanged.

A separate, MFA-gated approver can now record one final, append-only decision
on an exact repository package: `authorized_for_publication` or `rejected`,
with a required reason. The package creator cannot authorize their own package.
TekDocs re-verifies the signed evidence and every retained artifact before
recording either outcome. The decision has exact-Workspace isolation and an
audit event. Authorization permits a later publisher to create a publication
record; it does not itself permit client distribution, enqueue notifications,
or change the legacy STATIC publisher or portal routes.

An MFA-gated publisher can now create one signed, append-only repository STATIC
record from an authorized package. Its manifest binds the final authorization,
package and evidence digests, exact Git commit, and retained HTML, PDF, and
attachment descriptors. Creation re-verifies the retained chain; later
verification checks the signature, trusted key, manifest, and retained bytes
without consulting the live Git head. A staff-only summary route reports
integrity but exposes no artifact bytes or client access. This record is not
released for distribution: lifecycle decisions, supersession policy, and client
delivery are separate gates.

The next internal gate records append-only release and withdrawal decisions
against a signed repository STATIC record. An MFA-enabled approver other than
the record creator can release only while the complete retained chain verifies.
A release is refused when another active release exists for the same Workspace
document without naming it as the explicit predecessor of a replacement. An approver can
withdraw a released record even if retained bytes have since become unavailable,
so bad material need not stay marked released. Database guards serialize these
decisions by document, enforce exact scope and action order, and prevent edits
or deletion. The staff route reports state and audit reasons, but neither
release nor withdrawal grants a client route, download, notification, or
authority handoff.

An independently signed and authorized replacement can now supersede the one
current active release for the same exact Workspace document. Its release
event names the predecessor; the predecessor becomes permanently `superseded`
without modifying its signed record or historical release event. The database
serializes the replacement and rejects a missing, wrong-scope, withdrawn, or
already superseded predecessor. Only the replacement can then be withdrawn;
withdrawing it does not reactivate the prior record. The staff API exposes the
link and state, while client routes and delivery remain closed.
PostgreSQL composition tests cover an unauthorized or absent predecessor,
atomic replacement of an active release, permanent prior-record supersession,
withdrawal of the replacement despite missing retained bytes, direct database
guard refusal, client-portal denial, and the `0175`→current migration path.
The Docker-backed `make test-content-composition` and repository-wide
`make check` gates passed locally for this slice. No production deployment,
client delivery, or authority handoff is claimed.

The next internal step records an explicit, one-per-record client-delivery
authorization after release. A distinct MFA-enabled approver must recheck the
signed source and retained artifacts, plus the current client visibility of
every frozen entity reference. PostgreSQL enforces exact Workspace ownership,
client audience, an active release, creator separation, and append-only
retention. Staff can inspect whether the authorization is currently effective;
withdrawal, supersession, artifact loss, or reference-visibility loss makes it
ineffective without deleting its audit trail. The permission inventory now
includes the repository-publication routes. No portal route, client download,
notification, production deployment, or authority handoff is added.
The Docker-backed `make test-content-composition`, repository permission
matrix, and repository-wide `make check` gates passed locally for this slice.
