# TekDocs 0.1.7 versioned custom fields evidence

Date: 2026-08-08

Status: verified locally; hosted GitHub workflows remain pending publication and a pull request.

## Delivered scope

- Stable custom-field definitions belong either to the MSP or one organization, target a single Entity type, and retain an immutable key, target, and ownership identity.
- Editing definition presentation or validation rules appends an immutable, sequential version. Each version records its label, description, required marker, type, server-generated JSON Schema, display order, author, and creation time.
- Text, integer, number, boolean, date, HTTP(S) URL, email, choice, and multi-choice fields validate with JSON Schema Draft 2020-12 plus format checks. The API does not accept caller-supplied schemas, executable field types, or secret fields.
- Entity values use a strict version-pinned envelope. An incompatible new definition version reports its migration impact while retaining the prior value and exact schema version until an explicit edit.
- MSP definitions are inherited by matching records in organization workspaces. Organization definitions stay private to their owning organization and cannot be mutated through another scope.
- Route-derived APIs and PostgreSQL migration-owned guards enforce tenant, organization, target-type, definition-version, archive, envelope-shape, and immutable-history boundaries.
- The Custom Fields interface provides definition creation, version history, impact reporting, inherited read-only presentation, and archival in MSP and organization contexts.
- Site and Location records provide the first generic custom-value editor, including responsive and keyboard-accessible controls plus loading, empty, validation, denial, stale-version, and stale-workspace handling.

## Known boundaries

- Custom fields are metadata, not a secret store. Secret values are deliberately rejected and remain assigned to the dedicated encrypted-provider milestone.
- Organization-defined fields currently target Sites and Locations. The domain contract already supports Person and Organization targets for later value-entry workflows, without widening this slice.
- A `required` marker controls future record forms and reporting; this slice does not retroactively reject an existing record that lacks a value.
- Bulk migration tools, reporting/search indexes, imports, field groups, conditional presentation, and per-definition RBAC remain later work.
- Local Compose intentionally permits HTTP and therefore reports Django's HTTPS-redirect deployment warning. The production-image rehearsal enforces the production settings contract.
- PostgreSQL RLS, database-enforced audit immutability, secret-file enforcement, reproducible supply-chain inputs, backups, hosted automation evidence, and the editor bundle warning remain tracked in the engineering risk register.
