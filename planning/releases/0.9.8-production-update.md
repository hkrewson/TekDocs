# 0.9.8 explicit production release selection

## Scope and reproduction

This release-operations correction adds `--release v0.9.8` to the updater. The
reported `unknown argument: --release` was reproduced with the original script
before editing. The prior recommendation named an unimplemented option. The
production output supplied by the operator identified main commit 5c9a64f and
three older image digests; the updater had correctly followed its upstream rather
than selecting the separately published 05abb13 release.

Acceptance: an installed updated script must select the reviewed release commit,
use the tagged Compose files and exact approved image digests, retain backup and
migration/readiness gates, and verify running service identities before recording
success. The frozen application, schema, API and image artifacts are unchanged.

## Implemented

- A strict non-executable four-field receipt binds v0.9.8 to the previously
  published/verified commit and backend/frontend/diagram-renderer digests.
- Release mode fetches the exact tag without forcing tag replacement, checks its
  commit and VERSION, and requires a forward ancestry relationship from the
  running backend's revision. Missing/unverifiable revisions and backward updates
  fail closed. It retains the existing encrypted-backup default.
- All three commit-addressed image pulls and revision-label checks remain active;
  their resolved digests must additionally equal the reviewed receipt before
  stopping application services or migrating.
- Tagged Compose files come from a temporary Git archive; the original project
  directory and environment file are retained. The tooling checkout is unchanged,
  including when detached. No upstream is needed in release mode. The archive is
  removed at exit and is not used as a persistent data/secret mount.
- After migration and public readiness, backend, worker, scheduler, frontend and
  diagram-renderer must be running with the reviewed image references. Only then
  are deployment digests and TEKDOCS_DEPLOYED_COMMIT persisted. The checkout SHA
  identifies tooling in this mode, not the deployed application.
- Without --release, existing upstream behavior is preserved. Release mode is the
  explicit path for published images; missing receipts are not inferred from tags.

## Verified

- Original parser reproduction failed for the reported missing option.
- `make test-automated-security-review-gate`: 96 tests, three expected live skips.
- Seven updater contract tests passed inside a Linux Docker container, with
  disposable real Git histories and mocked Docker/curl/backup operations. These
  cover exact-image selection, preserved tooling checkout, legacy upstream mode,
  invalid/missing release, tag mismatch, backward update, revision/digest mismatch,
  wrong running image, backup failure and migration failure. Backup precedes pulls;
  preflight rejection never stops services; failures never persist success.
- Real Docker Compose parsed the actual 05abb13 archive and production overlays:
  all six application/migration services select approved digests, no build fallback
  remains, and named volumes retain the selected project's identity.
- `make test-production-setup`, Bash syntax, whitespace and Wiki checks passed.
- `make release-status` remains green with zero verification blockers for 05abb13.

The first macOS contract run exposed a fixture path-alias comparison; resolving
its temporary root fixed that fixture. The first Linux container lacked Bash;
installing Bash only in the disposable test container allowed the actual host
script to run. No runtime image or production dependency was changed for testing.

## Boundaries and delivery

This is verified deployment-tooling behavior, not a completed production rollout.
No production database, services or configuration were changed by these checks.
The operator must first fetch/install this tooling revision, then invoke release
mode using existing backup settings. Checking out v0.9.8 alone selects the frozen
older updater and does not install this correction. No merge into main, additional
image publication or Wiki publication is implied by the tooling branch push.

The Wiki upgrade procedure is updated locally. The public Upgrade-and-rollback
page returned 404 during this work; local Wiki publication remains separately
controlled. Unrelated Wiki and release-record edits were preserved.
