# TekDocs 0.1.14 runtime isolation and reproducible-input evidence

Date: 2026-08-09

Status: verified locally; hosted GitHub execution remains externally blocked pending explicit repository-publication authorization.

## Delivered scope

- Docker Compose now separates the PostgreSQL migration owner from the fixed `tekdocs_runtime` application role. A one-shot migration service owns schema changes and runtime-role provisioning; web, worker, and scheduler receive only runtime credentials.
- Production startup validates role identity and rejects superuser, owner, `BYPASSRLS`, or incomplete-policy configurations. The runtime role cannot create schema objects or modify Django migration records.
- Forced PostgreSQL RLS protects every implemented tenant-owned core table through a maintained policy inventory. Tenant and exact organization scopes use both `USING` and `WITH CHECK`; missing scope fails closed, and entity-link visibility requires both endpoints to be visible.
- Authenticated session requests execute inside one atomic boundary. TekDocs binds the installation tenant before domain access and, after CSRF processing, rebinds organization routes to the URL workspace before the central policy service authorizes the operation.
- Explicit RLS helpers provide fail-closed transaction-local scope for workers and management commands. Bootstrap, invitation acceptance, and audit creation bind scope only when their trusted tenant is known.
- Python build, production, and development dependencies now resolve from hash-locked inputs. External Docker images and Dockerfile bases are digest-pinned; GitHub Actions use annotated immutable commit SHAs; local checks reject drift.
- The production backend image removes pip, setuptools, and their independently versioned vendored libraries after construction. Local and hosted image scanning now targets the production artifact.
- Runtime migration, clean-install, upgrade, production-image, and real browser journeys use the normalized owner/runtime Compose boundary.
- OpenAPI, architecture, threat model, security guidance, engineering risks, ADR 0017, and the roadmap describe the same boundary.

## Verification

- The complete local gate components passed at `0.1.14`: formatting, Ruff, mypy across 67 source files, migration and OpenAPI drift, action workflow lint, supply-chain pin validation, frontend lint/type/build, and unit/component suites.
- Host-shaped backend tests passed 416 tests with 16 expected PostgreSQL-only skips and 86.58% coverage. The production-shaped PostgreSQL suite passed 432 tests at 91.18% coverage.
- Dedicated raw-connection RLS tests passed role-attribute, missing-scope, MSP-scope, exact-organization, cross-tenant, sibling-write, unrestricted-mode, schema-denial, inventory, and connection-cleanup cases.
- Chromium, Firefox, and WebKit passed all 84 browser tests. The independent non-mocked browser-to-proxy-to-Django-to-PostgreSQL workspace journey passed and verified its database fixture.
- `pip-audit`, Bandit, npm audit, Gitleaks, and High/Critical Trivy scans of the production backend, frontend, and Mailpit images reported no actionable findings.
- Production-target startup, a clean `0.1.14` installation, and a preserved-data `0.1.3` to `0.1.14` upgrade rehearsal passed.

## Assigned risk disposition

- `TD-RISK-002` — **implemented for the current core boundary.** Active forced RLS and a non-owner runtime credential now provide database-level isolation for implemented tenant-owned tables. Each future tenant-owned table must join the blocking policy inventory; final identity/policy-boundary certification remains `0.2.0`.
- `TD-RISK-009` — **reproducible inputs implemented.** Hash locks, digest/SHA pins, drift checks, production scanning, and build-tool removal materially reduce supply-chain variance. Signed published images, SBOM attestations, and provenance remain correctly assigned to `0.9.4`.
- `TD-RISK-010` — **externally blocked, not verified.** Workflows lint locally, but TekDocs has not been published or pushed because the user has not authorized that external action. Hosted CodeQL, dependency review, browser-matrix, artifact, and branch-protection evidence cannot honestly be claimed yet.

## Known boundaries

- Authentication-provider tables and the tenant authorization control plane intentionally remain outside organization RLS. They remain tenant-scoped through the central policy boundary and are part of final `0.2.0` certification.
- Resolving an organization route into database scope establishes visibility, not authorization. The central policy service remains mandatory for every operation.
- Worker and management-command code must enter an explicit `rls_scope`; background work without a trusted tenant fails closed by design.
- Development and migration images retain build/test tooling and are not release artifacts. The shipped production backend removes that tooling and is the image-scanning target.
- Secret-file injection remains planned rather than implemented; `TD-RISK-004` retains its `0.3.1` implementation and `0.8.7` production-enforcement milestones.
- Hosted automation remains pending explicit authorization to publish/configure the repository. No push, tag, deployment, or branch-protection change was performed for this slice.
